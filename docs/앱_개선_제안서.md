## 0. 한눈에 보기

현재 앱은 **동작하는 2AFC(2지 선다) 음고 변별 훈련기**로 골격이 잘 잡혀 있습니다.
계층 분리(`AudioEngine` / `StaircaseEngine` / `SessionManager` / `Storage` / 화면)가 명확하고,
cent↔Hz 변환·클램프·프리셋 저장 등 도메인 로직이 순수 함수로 떨어져 있어 확장하기 좋은 상태입니다.

다만 **측정값의 신뢰도를 깨뜨리는 결함이 4건** 있고, 이것들은 기능 추가보다 먼저 처리해야 합니다.
아래 표가 전체 요약입니다.

## 1. 현재 앱 파악

### 1.1 구조

```
app/                       expo-router 파일 라우팅 (Stack, headerShown:false)
├─ _layout.tsx             전역 다크 배경·StatusBar
├─ index.tsx               홈: 메인 카드 1 + 서브 카드 2 + 고지문
├─ training.tsx  (560줄)   훈련 화면 — 상태·타이머·재생·채점 전부 여기
├─ stats.tsx     (341줄)   요약 타일 4 + 최근 세션 10건
└─ settings.tsx  (325줄)   기준음 프리셋 3 + 데이터 초기화 + 고지문

src/
├─ audio/AudioEngine.ts    AudioContext, sine / sawtooth+bandpass×2
├─ audio/pitchUtils.ts     centsToFreq, freqToCents, calcCoupledDuration, clampFreq
├─ audio/keyzoneUtils.ts   최근접 샘플 선택 + detune  ← 작성됐지만 어디서도 호출 안 됨
├─ training/StaircaseEngine.ts   2-down-1-up 계단법 (10 cent 고정 스텝)
├─ training/SessionManager.ts    세션 수명주기 + 시행 기록
├─ storage/*.ts            AsyncStorage 2종 (세션 / 설정)
├─ components/*.tsx        ModeTab, AnswerButtons, FeedbackCard, SkiaWaveVisualizer
│                          + WaveVisualizer.tsx (사용처 없음 — 사문화)
└─ constants/theme.ts      COLORS / SPACING / RADIUS / FONT_SIZE / AUDIO / STAIRCASE / KEYZONE
```

### 1.2 한 시행(trial)의 흐름

```
[소리 듣기] 탭
  → (세션 비활성 시) 프리셋 로드 → SessionManager.startSession()
  → AudioEngine.ensureRunning()
  → SessionManager.prepareRound()   ← isHigher 랜덤 결정, targetFreq 계산
  → A 재생 1.0s ─ setTimeout ─ 0.5s 무음 ─ setTimeout ─ B 재생 1.0s
  → setTimeout → gameState='waiting'  (답변 버튼 활성)
  → 높음/낮음 탭 → submitAnswer() → 계단법 갱신 → FeedbackCard
  → 3회 이상 시 [세션 종료 및 저장] 노출 → AsyncStorage 저장 → Alert
```

### 1.3 잘 되어 있는 점

- `AudioEngine`이 `ensureRunning()`으로 suspended 컨텍스트를 사용자 제스처 시점에 깨움 — Android에서 흔히 놓치는 부분인데 처리돼 있습니다.
- `clampFreq`가 `{ clamped, wasOverLimit }`를 반환하고 `StaircaseEngine`이 `clampCount`로 집계 → 세션 결과에 저장. 파일럿 검증 설계가 코드에 반영돼 있습니다.
- `SessionResult.baseFreq` / `clampCount`가 optional로 선언돼 구버전 저장 데이터와의 호환을 고려했습니다 (`SessionManager.ts:34-37`).
- `AppSettingsStorage`가 저장값을 `VALID_PRESETS`로 검증 후 fallback — 손상된 값에 안전합니다.
- 훈련 데이터와 앱 설정 저장소를 분리한 것도 적절합니다.

## 2. P0 — 측정 신뢰도를 깨뜨리는 결함

> 이 6건은 **저장된 통계 숫자를 믿을 수 없게 만듭니다.** 다른 작업보다 먼저 처리할 것을 권합니다.

### P0-1. 같은 자극에 답을 여러 번 낼 수 있음 (점수 조작 가능)

`app/training.tsx:363`
```tsx
<AnswerButtons disabled={gameState === 'playing' || gameState === 'idle'} ... />
```
`app/training.tsx:218`
```tsx
if (gameState !== 'waiting' && gameState !== 'answered') return;
```

답변 후 상태는 `'answered'`인데, 이 상태에서도 버튼이 **활성이고 핸들러도 통과**합니다.
`isHigher`는 다음 `prepareRound()`까지 그대로이므로, 피드백으로 정답을 본 뒤 같은 버튼을 계속 누르면
**시행 수·정답 수·연속이 무제한으로 쌓이고 난이도(cent)도 계속 내려갑니다.**

- 영향: `totalTrials`, `correctCount`, `accuracy`, `minCentsAchieved` 전부 오염. 통계 화면 수치 전부.
- 수정: `disabled`에 `gameState === 'answered'` 추가 + `handleAnswer`의 가드를 `if (gameState !== 'waiting') return;`로 축소.

### P0-2. "다시 듣기"가 정답을 다시 뽑음

`app/training.tsx:176`에서 재생 버튼은 상태와 무관하게 항상 `prepareRound()`를 호출하고,
`StaircaseEngine.prepareRound()`(`:81`)는 매번 `Math.random() > 0.5`로 방향을 새로 정합니다.

즉 **답하기 전에 한 번 더 듣기를 누르면 A/B 관계가 바뀝니다.**
사용자는 "같은 소리를 다시 듣는다"고 생각하는데 실제로는 새 문제입니다.
게다가 어려운 문제를 답하지 않고 계속 재생만 눌러 **회피**할 수 있어, 시행 표본이 편향됩니다.

- 참고: 명세서 §7 UI 목업의 버튼 문구도 `🔊 소리 다시 듣기 (A ➔ B)`로, 재생(replay) 의도가 맞습니다.
- 수정: 버튼을 두 역할로 분리
  - `waiting` 상태 → **다시 듣기**: `prepareRound()` 없이 현재 `targetFreq`로 재재생
  - `answered` 상태 → **다음 문제**: `prepareRound()` 호출
  - 다시 듣기 횟수를 `TrialRecord.replayCount`로 기록 (난이도 판단 지표로 유용)

### P0-3. 반응 시간이 자극 재생 시간을 포함

`SessionManager.ts:107` — `prepareRound()`에서 `roundStartTime = Date.now()`
`SessionManager.ts:116` — `submitAnswer()`에서 `Date.now() - roundStartTime`

시계가 **재생 시작 시점**부터 돌기 때문에, A(1.0s) + 갭(0.5s) + B(1.0s) = **2500ms가 항상 포함**됩니다.
통계 화면의 "평균 반응 시간"(`app/stats.tsx:112-118`)은 구조적으로 3000ms 이상만 나옵니다.

- 수정: `gameState`가 `'waiting'`이 되는 시점(= 답변 버튼 활성 시점)에 `markResponseWindowOpen()`을 호출하고 그때부터 측정.
- 다시 듣기를 허용한다면 마지막 재생 종료 시점 기준으로 재설정.

### P0-4. 톤이 지속되지 않고 계속 감쇠함

`AudioEngine.ts:128-133`
```ts
gain.gain.setValueAtTime(0.001, startTime);
gain.gain.exponentialRampToValueAtTime(0.4, startTime + AUDIO.ATTACK_TIME);   // 0.05s
gain.gain.exponentialRampToValueAtTime(0.001, startTime + duration - AUDIO.RELEASE_TIME);
```

두 번째 램프의 **종점이 0.95s**입니다. 즉 0.05s에 0.4까지 올라간 뒤
**0.05s → 0.95s 구간 내내 0.4에서 0.001로 지수 감쇠**합니다(약 52dB). 서스테인 구간이 없습니다.

- 결과: 1.0초 톤이라고 문서화돼 있지만 **체감 지속시간은 수백 ms**. 음고 변별은 자극 길이에 크게 의존하므로 역치가 실제보다 나쁘게 측정됩니다.
- voice 모드도 동일 패턴 (`AudioEngine.ts:177-182`).
- 수정 (ADSR 정상화):
  ```ts
  const susEnd = startTime + duration - AUDIO.RELEASE_TIME;
  gain.gain.setValueAtTime(0.001, startTime);
  gain.gain.exponentialRampToValueAtTime(peak, startTime + AUDIO.ATTACK_TIME);
  gain.gain.setValueAtTime(peak, susEnd);                      // 서스테인 유지
  gain.gain.exponentialRampToValueAtTime(0.001, startTime + duration);
  ```

### P0-5. A→B 간격이 JS 타이머에 의존 (오디오 클럭 미사용)

`app/training.tsx:187-201`에서 B는 `setTimeout` 콜백 안에서 `playTone(targetFreq, 0, ...)`로 재생됩니다.
`playTone`은 내부에서 `await ensureRunning()`을 한 번 더 거치므로 마이크로태스크 지연도 더해집니다.

Web Audio에는 이미 `startTimeOffset` 파라미터가 있는데(`AudioEngine.ts:89`) `0`만 넘기고 있어 **활용되지 않습니다.**
JS 스레드가 바쁘면 ISI(자극 간 간격)가 수십 ms 흔들리고, 이는 시간 단서로 작동할 수 있습니다.

- 수정: 재생 시작 시 두 톤을 **오디오 클럭에 한 번에 예약**
  ```ts
  await audioEngine.ensureRunning();
  audioEngine.playTone(baseFreq,  0,              duration, mode);
  audioEngine.playTone(targetFreq, duration + gap, duration, mode);
  ```
  UI 하이라이트만 `setTimeout`으로 두면 됩니다(시각은 정밀도가 덜 중요).

### P0-6. 앱 백그라운드 전환·헤드폰 분리 시 라운드가 계속 진행됨

`AppState` 구독이 어디에도 없습니다. 백그라운드로 나가도 `timersRef`의 타이머는 살아 있고,
돌아오면 소리를 못 들은 상태에서 답변 버튼이 활성화돼 있습니다.

- 수정: `AppState`가 `background`가 되면 `clearTimers()` + 라운드 무효화(`gameState='idle'`) + 사용자에게 "다시 들어주세요" 안내.
- 통화·미디어 인터럽션도 동일 처리.

## 3. P1 — 훈련 과학(psychophysics) 개선

### P1-1. "최소 음정 차이"는 역치가 아닙니다

현재 대표 지표는 `minCentsAchieved` — 세션 중 도달한 **최솟값**입니다(`SessionManager.ts:131-133`).
이것은 극단값이라 운(찍기)에 크게 흔들립니다. 2AFC에서 우연 정답률이 50%이므로,
운 좋게 두 번 연속 맞히면 실제 능력과 무관하게 값이 내려갑니다.

- 표준 방식: **반전(reversal) 기반 역치 추정.** 계단이 방향을 바꾼 지점(cent)들을 기록하고,
  초반 2~4개를 버린 뒤 **나머지 반전값의 평균(또는 기하평균)**을 역치로 씁니다.
  2-down-1-up 계단법은 이론적으로 **70.7% 정답 지점**에 수렴합니다.
- 구현 부담이 작습니다. `StaircaseEngine`에 `reversals: number[]`와 직전 이동 방향만 추가하면 됩니다.
- 화면 문구도 "최소 음정 차이" → **"변별 역치(cent)"**로 바꾸고, `minCentsAchieved`는 보조 지표로 남기면 됩니다.

### P1-2. 평가(Assessment) 모드가 훈련과 완전히 동일

`SessionManager`는 `config.mode`를 **결과 기록에만** 쓰고(`:147`), 동작을 전혀 분기하지 않습니다.
현재 "📋 평가" 버튼은 **라벨뿐**입니다.

특히 문제는 **평가 중에도 정답 피드백이 나온다**는 점입니다(`FeedbackCard`가 모드 무관 렌더링).
피드백은 학습 효과를 유발해 평가 결과를 왜곡합니다.

- 권장 분기:

  | 항목 | 훈련(Training) | 평가(Assessment) |
  |---|---|---|
  | 시행별 정답 피드백 | 표시 | **숨김** (세션 끝에 요약만) |
  | 종료 조건 | 사용자 임의 | **반전 N회(예: 8회) 또는 최대 시행 수 도달 시 자동 종료** |
  | 시작 난이도 | 직전 세션 역치 이어받기 | 매번 고정 시작값 |
  | 캐치 트라이얼 | 없음 | 아주 쉬운 문항(예: 400 cent) 10% 삽입 → 집중도 검증 |
  | 결과 | 진척용 | 역치 + 신뢰구간 리포트 |

### P1-3. 시작 난이도 50 cent는 초심자에게 과함

`STAIRCASE.INITIAL_CENTS = 50` (`theme.ts:125`). 사용법 문서(§4)에도
"차이가 크게 들리지 않는 것이 정상"이라고 적혀 있는데, 이는 **초기 이탈 요인**입니다.
대상 사용자(보청기·인공와우 착용자)의 음고 변별 역치는 반음(100 cent)을 크게 넘는 경우가 흔합니다.

- 권장: **쉬운 값에서 시작해 내려오는 구조**
  - 훈련 시작값을 200~300 cent로 올리고, 초반에는 큰 스텝(예: 50 cent)으로 빠르게 하강
  - 첫 반전 이후 스텝을 20 → 10 cent로 축소 (가변 스텝 계단법, 표준 기법)
  - 이러면 초심자는 첫 문제를 맞히며 시작하고, 숙련자는 5~6시행 만에 자기 수준에 도달합니다
- 두 번째 세션부터는 직전 역치의 1.5~2배에서 시작하면 시행 수를 크게 아낄 수 있습니다.

### P1-4. 레벨 로빙(level roving) 부재 — 음량 단서 차단 안 됨

두 톤 모두 고정 게인(wave 0.4 / voice 0.3)입니다. 기기·이어폰의 주파수 응답 차이 때문에
주파수가 다르면 **출력 음량도 미세하게 달라질 수 있고**, 사용자가 음고 대신 음량으로 답할 수 있습니다.

- 표준 대응: 시행마다 각 톤의 레벨을 **±4~6 dB 범위에서 독립 랜덤화**.
- 구현: `playTone`에 `gainDb` 파라미터 추가, `peak * Math.pow(10, rovingDb / 20)`.

### P1-5. 기준음 A가 항상 같은 주파수 → 절대 기준 암기 가능

`baseFreq`가 세션 내내 고정(440/330/262)이라, 사용자는 A를 무시하고 B만 절대 판단하는
전략을 학습할 수 있습니다. 이는 "두 소리의 비교"라는 과제 정의를 벗어납니다.

- 표준 대응: 시행마다 기준음을 **±100~200 cent 범위에서 랜덤 이동**(roving), 그 위에 ±cent 차이를 얹기.
- 프리셋(표준/중역/저역)은 **로빙의 중심값**으로 재정의하면 기존 UI를 그대로 유지할 수 있습니다.
- `clampFreq`가 이미 있으므로 안전망은 확보돼 있습니다.

### P1-6. 제시 순서가 항상 "기준 → 비교"

2I-2AFC(2구간 2지선다)에서는 보통 **어느 구간이 더 높은가**를 묻고 구간 순서를 랜덤화합니다.
현재는 "A 대비 B"로 고정이라 P1-5의 암기 전략과 결합해 과제 난도를 인위적으로 낮춥니다.

- 대안 A(작은 변경): 순서는 유지하되 P1-5의 기준음 로빙만 도입 — 실용적 절충.
- 대안 B(정석): "첫 번째가 높음 / 두 번째가 높음"으로 질문을 바꾸고 순서를 랜덤화.

### P1-7. 연속(streak) 배지가 항상 0 또는 1

`StaircaseEngine.ts:139`
```ts
streak: newStreak >= STAIRCASE.STREAK_THRESHOLD ? 0 : newStreak,
```
2회 연속 정답 시 계단 하강과 함께 `streak`을 0으로 리셋합니다. 이 값이 그대로 UI 배지
`🔥 연속: {streak}회`(`training.tsx:321`)에 쓰이므로 **1을 넘는 숫자를 볼 수 없습니다.**
사용법 문서에는 "연속으로 맞힌 횟수"라고 안내돼 있어 문서와 동작이 어긋납니다.

- 수정: 계단 제어용 카운터(`stepCounter`)와 표시용 누적 연속(`displayStreak`)을 **분리**.

## 6. P4 — 접근성 (a11y)

### P4-1. 접근성 속성이 전무

전 코드에서 `accessibilityLabel` / `accessibilityRole` / `accessibilityState` / `accessibilityHint`
**사용 0건**입니다. `TouchableOpacity`가 기본 role을 주긴 하지만 라벨이 이모지+텍스트 혼합이라 읽기가 어색합니다.

- 최소 작업: 모든 `TouchableOpacity`에 `accessibilityRole="button"` + 명시적 `accessibilityLabel`,
  비활성 버튼에 `accessibilityState={{ disabled }}`, 선택 탭에 `{{ selected }}`.

### P4-2. 터치 타깃이 Android 최소 크기(48dp) 미만

- `sessionModeBtn`: `paddingVertical: SPACING.sm(8)` + 텍스트 13px → 약 **34dp** (`training.tsx:448`)
- `backButton`: `paddingVertical: SPACING.xs(4)` (`stats.tsx:210`, `settings.tsx:188`) → 약 **26dp**
- `ModeTab.tab`: `paddingVertical: SPACING.md(12)` → 약 **42dp** (`ModeTab.tsx:60`)

- 수정: `minHeight: 48` 지정 또는 `hitSlop` 부여.

### P4-3. 폰트 확대 시 레이아웃 파손

`SkiaWaveVisualizer`의 `CANVAS_HEIGHT = 180` 고정 안에 라벨·주파수 텍스트가 들어갑니다.
시스템 글꼴 크기를 크게 설정하면 잘립니다. 배지 행도 `flexWrap`은 있으나 높이가 밀립니다.

- 수정: 캔버스 컨테이너 높이를 `minHeight`로 바꾸고 텍스트 영역을 캔버스 밖으로 분리.

### P4-4. 색상만으로 A/B를 구분

시안/오렌지 조합 자체는 색각 이상에서도 비교적 안전하지만, 텍스트 라벨과 위치가 보조하고 있으니 현재도 큰 문제는 아닙니다.
다만 정답/오답 피드백은 **초록/빨강 + 배경색**에 의존합니다 — 아이콘(✓/✗)을 함께 넣으면 안전합니다.

### P4-5. 햅틱 피드백 미사용

`expo-haptics`가 설치돼 있으나 **호출 0건**입니다.
청각 보조 기기 사용자 대상 앱에서 촉각 피드백은 특히 가치가 큽니다.

- 정답: `notificationAsync(Success)` / 오답: `notificationAsync(Error)` / 톤 시작: `impactAsync(Light)`
- 설정에서 on/off 제공.

### P4-6. 모션 감소 설정 미대응

Skia 반복 애니메이션·화면 전환이 항상 재생됩니다. `AccessibilityInfo.isReduceMotionEnabled()`를 확인해 정적 표시로 대체하는 옵션을 두면 좋습니다.

## 8. P6 — 릴리스 준비

### P6-1. `app.json`이 템플릿 잔재 상태 ⚠️

```json
"name": "청능 애플리케이션",
"slug": "threads-clone",
"scheme": "threadc",
"android": { "package": "com.vlondy.threadsclone" },
"icon": "./assets/images/splash.png"
```

- `slug` / `scheme` / `package`가 전부 **"threads-clone" 템플릿 잔재**입니다.
  `package`는 스토어 등록 후 **변경 불가**이므로 출시 전에 반드시 확정해야 합니다.
- 앱 이름 **"청능 애플리케이션"**이 문제입니다. 명세서 §1의 규제 방어 용어 가이드는
  **청력 검사·청각 재활·치료 계열 용어를 금지**하고 있는데, "청능(聽能)"은 청능재활(aural rehabilitation)을
  직접 연상시키는 임상 용어입니다. 앱 내부는 "HarmoniTune / 하모니 튠 / 음고 인지 감각 훈련"으로 일관되게
  써 놓고 **스토어에 노출되는 이름만 임상 용어**인 상태입니다. `"name": "하모니튠"`으로 통일 권장.
- 아이콘이 `splash.png`를 재사용 중입니다. 앱 아이콘 / 적응형 아이콘 전경 / 스플래시는 각각 다른 규격이 필요합니다.

### P6-2. `expo-updates`가 설치돼 있으나 설정 없음

OTA 업데이트를 쓸 계획이면 `updates` / `runtimeVersion` 설정이 필요하고, 아니라면 제거하세요.

### P6-3. 화면 방향

`"orientation": "default"`(자유 회전)인데 레이아웃은 세로 전제입니다(고정 캔버스 등).
`"portrait"`로 고정하거나, `expo-screen-orientation`(이미 설치됨)으로 훈련 화면만 잠그세요.

### P6-4. 세션 중 화면 꺼짐

훈련은 소리 듣고 답하는 간격이 있어 화면이 꺼질 수 있습니다. `expo-keep-awake`로 세션 중 유지 권장.

### P6-5. 개인정보 처리방침 / 데이터 고지

로컬 전용이라도 스토어 심사에서 개인정보 처리방침 URL을 요구합니다.
"모든 데이터는 기기 내에만 저장되며 외부로 전송되지 않습니다"를 설정 화면에도 명시하면 신뢰도가 올라갑니다.
