# 기준음 선택 · 주파수 클램프 구현 계획

현재 앱은 기준음(소리 A)이 항상 **440 Hz**로 고정되어 있고, 저역으로 바꾸거나 고역을 막는 코드가 없습니다.  
이 문서는 그 상태를 바꾸기 위한 **구현 계획**입니다. (코드 변경 전 설계용)

---

## 1. 목표

| 목표 | 설명 |
|------|------|
| 기준음 선택 | 설정에서 기준 주파수를 고를 수 있게 함 (표준 440 / 중역 330 / 저역 262) |
| 고주파 배제 | 프리셋은 **`standard` / `mid` / `low`만**. 고역 프리셋(440 초과)은 두지 않음 |
| 세션 반영 | 선택한 기준음이 훈련 세션의 `baseFreq`로 전달됨 |
| 주파수 클램프 | A·B가 허용 대역을 벗어나면 Hz를 잘라 안전한 자극만 재생 (안전망) |
| UI 정합 | 설정·훈련 화면의 “440 Hz” 고정 표시를 실제 선택값과 맞춤 |

기본값 **440 유지** — 기존 UX 충격을 최소화한다.

비목표(이번 범위 밖):

- 연속 가변 슬라이더(Hz 자유 입력)
- 의료/청력도 연동
- 키존 실녹음 샘플맵 자동 전환
- 고역 기준음 프리셋

---

## 2. 현재 상태 (As-Is)

- 상수: `src/constants/theme.ts` → `AUDIO.BASE_FREQ = 440`
- 엔진: `StaircaseEngine` / `SessionManager`는 `baseFreq`를 받을 수 있으나, UI에서 항상 기본값만 사용
- 설정: `app/settings.tsx`에 “A4 = 440 Hz” 배지만 표시 (선택 불가)
- 시각화: `WaveVisualizer` / `SkiaWaveVisualizer`에 `440 Hz` 라벨 고정
- 클램프: `keyzoneUtils.clampDetune`은 **detune cent**용이며, 재생 Hz 상·하한과는 별개

현실적 범위: 엔진이 이미 `baseFreq`를 받으므로 **UI·저장·클램프·세션 메타**만 연결하면 된다.

## 3. 제안 UX

### 3.1 프리셋 (3단 · 확정)

| 키 | 표시 이름 | 기준 Hz | 용도 |
|----|-----------|---------|------|
| `standard` | 표준 (A4) | **440** | 기본값 · 일반 훈련 |
| `mid` | 중역 | **330** | CI E4 앵커 · 한 단계 낮은 체감 |
| `low` | 저역 | **262** (≈ C4) | CI middle C 비교·파일럿 기록용 |

고역 프리셋은 없다. Hz 값은 `theme.ts` 상수로 두어 이후 조정은 상수만 바꾸면 된다.

### 3.2 설정 화면

- `app/settings.tsx`의 “기준 음고” 행을 **선택 UI**로 변경
- 3개 프리셋 중 하나 선택 — **3행 탭 또는 세그먼트** (설정 화면 톤에 맞춤)
- 선택값을 AsyncStorage에 저장 → 앱 재시작 후에도 유지

### 3.3 훈련 화면

- 세션 시작 시 저장된 프리셋 → `baseFreq`로 `SessionManager`에 전달
- 파형 라벨: 고정 `440 Hz` 대신 **실제 `baseFreq` Hz** 표시
- 본훈련 검증은 **wave 우선**. voice 포먼트(F1/F2 고정)는 후속

## 4. 주파수 클램프 정책

### 4.1 왜 필요한가

기준음을 낮추거나, cent 격차가 클 때(최대 300 cent) B의 Hz가 과도하게 올라가/내려가  
기기·청취에 부담이 되거나 자극이 불안정해질 수 있습니다.  
현재 프리셋·`MAX_CENTS=300` 조합에서는 아래처럼 **거의 걸리지 않는 안전망** 수준이다.

### 4.2 한도 · 숫자 검증

| 상수 | 값 | 의미 |
|------|-----|------|
| `FREQ_MIN_HZ` | **200** | 재생 하한 |
| `FREQ_MAX_HZ` | **2000** | 재생 상한 |

경계 케이스 (대략):

| 조합 | 계산 | 한도와의 관계 |
|------|------|----------------|
| 저역 하향 | 262 − 300 cent ≈ **220 Hz** | `FREQ_MIN 200` 바로 위 → 하한 근처, 클램프 거의 없음 |
| 표준 상향 | 440 + 300 cent ≈ **523 Hz** | `FREQ_MAX 2000`과 한참 여유 |
| 중역 상·하향 | 330 ± 300 cent ≈ 278 / 392 Hz | 한도 안 |

→ 현재 프리셋·300 cent 조합이면 클램프는 **거의 안전망**이다.

### 4.3 UX · 로깅

- 사용자에게는 **조용히** 처리 (토스트/배지 없음, 1차)
- 정답 판정은 Hz가 아니라 **방향(높음/낮음)** 이므로 클램프돼도 판정 로직은 유지된다
- 다만 통계의 **달성 cent**와 **실제 A–B 간격**이 어긋날 수 있으므로,  
  파일럿용으로 **클램프 발생 횟수**를 개발 로그(또는 세션 메타 카운터)로 세는 것을 **권장**

### 4.4 적용 위치

1. `pitchUtils`에 `clampFreq(hz, min, max)` 유틸 추가
2. `StaircaseEngine.prepareRound`에서 `targetFreq` 산출 직후 클램프  
   → 엔진 상태가 곧 “실제 재생 Hz”와 일치
3. (방어) `AudioEngine.playTone` 입구에서도 한 번 더 클램프해도 무방

cent 난이도(`centsDifference`)는 **그대로 유지**합니다.  
클램프는 “스피커로 나가는 Hz”만 보정하고, 계단법 점수·기록 단위는 cent를 유지합니다.

> 어긋남이 파일럿에서 문제면 “클램프 시 방향 재추첨” 또는 “해당 방향 스킵”을 2차로 검토한다.

## 5. 데이터 · 저장

### 5.1 저장 키

```text
@harmonitune/reference_pitch_preset
```

값 예: `"standard" | "mid" | "low"`

### 5.2 저장소

- 기존 `TrainingStorage`에 설정 getter/setter를 추가하거나  
- `AppSettingsStorage`(소형)를 분리 — 세션 데이터와 설정 데이터 혼선을 줄이려면 분리 권장

### 5.3 세션 기록

`SessionResult` / 세션 메타에 `baseFreq`(또는 프리셋 키)를 남긴다.  
파일럿에서 “440 vs 262” 비교 분석에 필수에 가깝다.  
(`docs/cent_활용과_시작간격.md` §5.3의 CI 비교 기록 권고와 정합)

권장(선택→권장): 세션 또는 개발 로그에 `clampCount`(클램프 발생 횟수)도 남긴다.

## 7. 구현 단계

### Step A — 상수·유틸 (로직만) ✅ 완료 (2026-08-04)

1. 프리셋 맵(440/330/262) + 주파수 한도 상수 정의  
2. `clampFreq` 구현  
3. `StaircaseEngine`에 클램프 연결 · (권장) 발생 카운트  
4. (가능하면) 단위 테스트 또는 콘솔로 `centsToFreq` + 클램프 케이스 확인  
   — 특히 262−300≈220이 하한 위에 남는지  

결과: `reports/step-a-reference-pitch-clamp.md` 참고. 262−300≈220.31 → 클램프 미발생(안전망 확인).

### Step B — 설정 저장·UI ✅ 완료 (2026-08-04)

1. 프리셋 AsyncStorage 저장/로드  
2. `settings.tsx`에서 선택 가능하도록 변경 (3행 또는 세그먼트)  
3. 기본값 `standard`(440) 유지  

결과: `reports/step-b-reference-pitch-settings.md` 참고.

### Step C — 훈련 연동 ✅ 완료 (2026-08-04)

1. 훈련 진입 시 프리셋 → `SessionManager({ baseFreq })`  
2. 시각화·배지에 실제 Hz 표시  
3. 세션 결과에 `baseFreq` 저장 · (권장) `clampCount`
4. wave 모드로 1차 검증  

결과: `reports/step-c-reference-pitch-training.md` 참고.  
Android 실기기 wave 청취 확인은 Step D 체크리스트에서 수행.

### Step D — 문서·검증 ✅ 문서·정적 검증 완료 (2026-08-04)

1. `앱_사용법.md` 갱신  
2. Android에서 검증 체크리스트 수행  

결과: `reports/step-d-reference-pitch-docs-checklist.md` 참고.

## 9. 성능·부작용 메모

| 항목 | 영향 |
|------|------|
| AsyncStorage 읽기 | 훈련 진입·설정 화면에서 1회성 I/O — 체감 미미 |
| 클램프 연산 | `Math.min/max` 수준 — 성능 부담 없음 |
| cent↔실제 간격 불일치 | 현재 숫자면 거의 발생하지 않음. 발생 시 로그로 감시 |
| 포먼트 F1/F2 고정 | 저역에서도 포먼트 필터는 현재 800/1200 고정 — 목소리 모드 음색이 달라질 수 있음(후속 과제) |

부정 영향이 있다면 **포먼트 고정값과 저역의 조합**이 가장 유력합니다.  
1차는 wave(순수 파형) 위주로 검증하고, voice 모드는 후속으로 맞추는 편이 안전합니다.

| 항목 | 결정 |
|------|------|
| 중역 | **330 Hz** (CI E4 앵커) |
| 저역 | **262 Hz** (CI middle C 비교용) |
| 고역 프리셋 | **없음** (고주파 배제) |
| 기본값 | **440 Hz** (`standard`) |
| 클램프 UX | **조용히** (1차) |
| 클램프 로그 | **권장** (발생 횟수) |

→ §10이 닫혔으므로 **Step A부터 구현 가능**하다.

## 11. 한줄 요약

설정에서 기준음 프리셋(**440 / 330 / 262만**, 고역 없음)을 고르고, 재생 Hz는 상·하한으로 조용히 클램프하며(현재 조합에선 거의 안전망), 훈련·라벨·세션 기록(`baseFreq`, 권장 `clampCount`)이 그 값을 따르게 한다. wave 본훈련부터 검증한다.
