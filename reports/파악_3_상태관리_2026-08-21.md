## 1. 전역 상태 라이브러리가 없습니다

Context, Redux, Zustand 같은 것을 **하나도 쓰지 않습니다.** 화면 하나가 자기 상태를 다 들고, 아래 컴포넌트에는 props로 내려줍니다.

화면이 6개뿐이고, 화면끼리 나눠 가질 상태가 저장소 말고는 없어서 성립하는 구조입니다. 화면 사이에 넘기는 값은 딱 하나 — `[결과]`로 갈 때 붙는 `sessionId`이고, 그것도 라우터 파라미터로 넘어갑니다 (`training.tsx:230`).

`ask-state-management.md`가 경계하는 "지역으로 충분한데 전역에 올리기"나 "서버 데이터를 전역 상태에 통째로 복사하기"는 이 저장소에 해당 사례가 없습니다.

**전역이라 부를 만한 것은 딱 하나** — `src/utils/haptics.ts:12`의 `let enabled`입니다.

```
(enabled)@haptics 모듈    — 앱 전체가 공유. React 상태가 아님
```

모듈에 얹힌 변수라 값이 바뀌어도 **화면이 다시 그려지지 않습니다.** 진동을 울릴지 말지만 정하므로 다시 그릴 필요가 없어 문제가 되지 않습니다. 화면에 보이는 스위치는 `settings.tsx`의 별도 `useState`가 담당합니다.

## 2. 훈련 화면의 상태 지도 (`app/training.tsx`, `useState` 15개)

이 앱에서 상태가 몰려 있는 유일한 곳입니다.

```
(audioEngine)@훈련화면          — 지연 생성. 이후 바뀌지 않음
(sessionManager)@훈련화면       — 지연 생성. 이후 바뀌지 않음

(soundMode)@훈련화면            ← ModeTab 누름 (세션 중엔 잠김)
(sessionMode)@훈련화면          ← 모드 탭 누름 (세션 중엔 잠김)
(gameState)@훈련화면            ← 재생 / 답변 / 앱 이탈
(activeSound)@훈련화면          ← 타이머 3개
(feedback)@훈련화면             ← 답변 (훈련 모드만)
(isSessionActive)@훈련화면      ← 세션 시작·종료
(revealedTargetFreq)@훈련화면   ← 답변 (훈련 모드만)

── 아래 6개는 StaircaseEngine 값의 사본 ──
(centsDifference) (streak) (totalTrials) (correctCount) (reversalCount) (baseFreq)
```

### 엔진 두 개를 상태로 들고 있는 이유

```js
const [audioEngine] = useState(() => new AudioEngine());
const [sessionManager] = useState(() => new SessionManager());
```

`useState`에 함수를 넘기는 방식(지연 생성)이라 **처음 한 번만** 만들어집니다. 주석에도 "지연 초기화로 매 렌더마다 새로 만들지 않는다"(`:91`)고 적혀 있습니다. setter를 안 쓰므로 값은 영영 바뀌지 않습니다.

같은 방식이 `FeedbackCard.tsx:22-23`에도 있습니다.

## 3. 사본이 6개 있습니다

난이도·연속 정답 수·문항 수·정답 수·반전 횟수·기준 주파수 — 이 여섯의 **원본은 `StaircaseEngine` 안**에 있습니다. 화면은 그 값을 자기 `useState`에 베껴 두고 그립니다.

```
(centsDifference)@StaircaseEngine  ── 원본
        │
        └─ 복사 ─> (centsDifference)@훈련화면  ── 화면에 그리는 용도
```

베끼는 지점은 **세 곳뿐**입니다.

| 어디 | 언제 | 무엇을 |
|---|---|---|
| `training.tsx:201-206` | 세션 시작 | 6개 전부 초기화 |
| `training.tsx:293-294` | 라운드 준비 | 난이도·기준음 |
| `training.tsx:354-362` | 답변 | 6개 중 5개 + 공개할 Hz |

`ask-state-management.md`가 경계하는 **"같은 상태를 두 곳에 각각 저장"** 모양이 맞습니다. 다만 읽어 보니 사정이 있습니다.

**첫째, 다른 방법이 없습니다.** `StaircaseEngine`은 보통 클래스라 **값이 바뀌었다고 화면에 알려 주는 장치가 없습니다.** 화면이 다시 그려지려면 `useState`를 거쳐야 합니다.

**둘째, 베끼는 자리가 모여 있습니다.** 세 곳뿐이고 전부 화면 파일 안에 있습니다. 여기저기 흩어져 있지 않아 어긋날 자리가 적습니다.

**셋째, 사본이 기록으로 흘러가지 않습니다.** 저장되는 값은 화면 사본이 아니라 `sessionManager.endSession()`이 엔진에서 직접 꺼낸 값입니다 (`training.tsx:213`). **화면 사본이 틀려도 기록은 안 틀립니다.** 이게 이 구조에서 가장 중요한 지점입니다.

`getState()`가 복사본을 돌려주는 것(`StaircaseEngine.ts:114`)도 같은 방향입니다. 밖에서 받은 객체를 고쳐도 엔진 안의 값은 안 바뀝니다. 이 동작은 테스트로도 고정돼 있습니다(`StaircaseEngine.test.ts:53`).

## 4. 파생값을 상태로 저장하지 않았습니다 — 잘된 쪽

`ask-state-management.md`가 가장 경계하는 것은 **다른 상태에서 계산되는 값을 별도 상태로 저장하고 `useEffect`로 맞추는 것**입니다. 원본이 바뀌어도 안 따라와 낡은 값이 되기 때문입니다.

**이 저장소에는 그런 곳이 없습니다.** 계산되는 값은 전부 그때그때 계산합니다.

| 값 | 어떻게 얻나 | 어디 |
|---|---|---|
| `accuracy` (정답률) | `correctCount / totalTrials` | `training.tsx:385` |
| `thresholdProgress` (역치 진행도 문구) | 모드 + 반전 횟수로 계산 | `training.tsx:395-409` |
| `hidesTrialFeedback` | `!showsTrialFeedback(sessionMode)` | `training.tsx:411` |
| `handlePlayPress` | 상태로 두 함수 중 고르기 | `training.tsx:326` |
| `accuracy` (결과 화면) | `session.accuracy * 100` | `result.tsx:80` |
| `delta` (직전 대비) | 두 역치의 차 | `result.tsx:85-88` |
| `avgReaction` | 시행 반응시간 평균 | `result.tsx:90-96` |
| 그래프 좌표·최소/최대·개선폭 | `values`에서 계산 | `ThresholdChart.tsx:67-97` |
| `accuracyPct` (세션 카드) | `correctCount / totalTrials` | `stats.tsx:198` |

`useMemo`가 한 군데도 없는데, 위 계산들의 크기를 보면 그럴 만합니다(→ [#6 성능](./파악_6_성능_2026-08-21.md)).

## 5. 상태를 `ref`에 한 번 더 베낀 곳 — `isSessionActiveRef`

`app/training.tsx:119`, `:129-131`:

```js
const isSessionActiveRef = useRef(false);
useEffect(() => { isSessionActiveRef.current = isSessionActive; }, [isSessionActive]);
```

같은 값이 `useState`와 `useRef`에 둘 다 있습니다. 사본이 하나 더 늘어난 셈인데, 이유가 있습니다.

`useFocusEffect`의 의존성 배열이 비어 있습니다 (`:172`). 그래서 그 안의 함수는 **화면에 처음 들어왔을 때의 `isSessionActive`를 계속 붙잡고** 있습니다. 세션을 시작해도 그 함수 눈에는 여전히 `false`입니다.

`ref`는 상자 하나를 계속 가리키므로 항상 최신 값을 봅니다. 그래서 `:163`의 `if (isSessionActiveRef.current) return;`이 제대로 동작합니다 — **세션 중에는 기준음 프리셋을 반영하지 않는다**는 규칙이 여기 걸려 있습니다.

목적이 분명한 사본입니다. 다만 `useState`와 `useRef` 두 벌을 손으로 맞추는 구조라, 나중에 한쪽만 고치면 어긋납니다.

`timersRef`(`:118`)는 성격이 다릅니다 — 타이머 ID 목록은 화면에 그릴 것이 아니라 정리할 대상이므로 `ref`가 맞는 자리입니다.

## 7. 컴포넌트로 내려가는 상태 (끌어올린 상태)

props가 **한 단계만** 내려갑니다. 여러 단계 파고드는 곳(prop drilling)이 없습니다.

```
(gameState)@훈련화면 --disabled--> [AnswerButtons]
(feedback)@훈련화면 --message, isCorrect--> [FeedbackCard]
(soundMode)@훈련화면 --activeMode--> [ModeTab] --onModeChange--> 콜백으로 되돌아옴
(activeSound)@훈련화면 --activeSound--> [SkiaWaveVisualizer]
(recentSessions)@통계화면 --values--> [ThresholdChart]
```

자식은 값을 **읽기만** 하고, 바꿀 때는 콜백을 부릅니다. `ask-state-management.md`가 말하는 기본형(원본은 부모 하나, 자식은 콜백으로 요청)을 따르고 있습니다.

`SkiaWaveVisualizer` 안에는 자식 컴포넌트가 둘 더 있습니다(`SoundColumn` → `WaveBar`). 여기서는 애니메이션 공유값이 두 단계 내려가는데, 이건 React 상태가 아니라 Reanimated 값이라 성격이 다릅니다.

## 9. 이 축에서 눈에 띈 것

**원본이 흐려진 곳이 없습니다.** 난이도의 원본은 `StaircaseEngine`, 세션의 원본은 `SessionManager`, 설정의 원본은 저장소. 화면이 들고 있는 것은 전부 그리기 위한 사본이고, 사본이 기록으로 흘러가는 경로가 없습니다.

**파생값을 저장한 곳이 하나도 없습니다.** `ask-state-management.md`가 "낡은 값의 흔한 원인"으로 꼽는 패턴(`useState` + `useEffect` 동기화)이 이 저장소에는 없습니다.

**대신 손으로 맞춰야 하는 사본이 8개입니다** — 엔진 값 6개 + `isSessionActiveRef` + 진동 설정. 지금은 맞추는 자리가 모여 있어 관리되지만, 상태가 더 늘면 흔들릴 자리입니다.

**훈련 화면 하나에 `useState`가 15개입니다.** 나머지 화면은 0~3개인데 여기만 몰려 있습니다. 이 화면이 다섯 단계짜리 화면이자 소리·난이도·기록을 다 다루는 자리라 그렇습니다.

- **`useFocusEffect`의 의존성이 비어서 생기는 문제**를 `isSessionActiveRef`가 정말로 막고 있는지, 실행해서 확인하지 않았습니다. 코드를 읽고 판단한 것입니다.
- **Reanimated 공유값**(`SkiaWaveVisualizer`)이 React 상태와 어떻게 다르게 도는지는 라이브러리 동작에 기댄 설명입니다. 직접 확인하지 않았습니다.
- 상태가 15개인 화면이 실제로 몇 번 다시 그려지는지 **측정하지 않았습니다**(→ [#6 성능](./파악_6_성능_2026-08-21.md)).
