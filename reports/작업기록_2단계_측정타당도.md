**Q. 이렇게 간단한 앱인데 왜 수정사항이 많지?**

앱이 복잡해서가 아니라, "전반적인 것 모두"를 봐달라는 요청이었기 때문입니다.
찾은 약 50건의 구성은 이렇습니다.

| 등급 | 개수 | 성격 |
|---|---|---|
| P0 | 6 | 진짜 문제 (4건 수정 완료) |
| P1 | 7 | 측정 방식 개선 |
| P2 | 9 | 있으면 좋은 기능 |
| P3~P6 | 30 | 대부분 한 줄짜리 (색 값, 미사용 라이브러리 삭제, 파일명) |

> **비유.** 종합건강검진을 받으면 소견이 20개 나옵니다. 그중 당장 치료할 건 한두 개고
> 나머지는 "관찰" 또는 "생활습관"입니다. **항목이 많다고 몸이 나쁜 게 아닙니다.**
> 자세히 봤으니 많이 나온 겁니다.

다만 이 앱에는 특수 사정이 하나 있습니다. **할 일 앱이 아니라 측정 도구**라는 점입니다.
할 일 앱이 개수를 틀리면 짜증나는 정도지만, 측정 앱이 숫자를 틀리면 **틀린 줄 모른 채 믿게 됩니다.**

**Q. 회귀 테스트는 처음 들어봤다.**

앱 화면에 나타나지 않는 개발자 도구라 쓰는 분은 볼 일이 없습니다.
이름과 달리 내용은 단순합니다 — **스스로 실행되는 점검표**입니다.

> **비유.** 건물 리모델링 후 "수도 틀어보기, 전기 켜보기, 문 여닫아보기"를 손으로 확인하는 대신,
> 버튼 하나로 3초 만에 131가지를 다 확인하는 것뿐입니다.

솔직히, 4화면짜리 앱에 항상 필요한 건 아닙니다. 권한 이유는 하나입니다 —
**2단계에서 난이도 엔진을 통째로 뜯어고칠 예정이었기 때문**입니다.
기존 코드를 건드리는 순간이 바로 고친 게 되살아나는 순간입니다.

# 수정 내역

## ① P1-3 — 시작 난이도 200 + 가변 스텝

### 왜 고쳤나

시작값 50은 **반음의 절반**입니다. 앱 사용법 문서에도 "차이가 크게 들리지 않는 것이 정상"이라고
적혀 있었는데, 이건 처음 써 본 사람이 첫 문제부터 틀리고 포기할 만한 설정입니다.
게다가 이 앱의 주 대상인 보청기·인공와우 사용자는 훨씬 큰 차이부터 시작해야 하는 경우가 많습니다.

조정 폭도 문제였습니다. 항상 10씩만 움직이니 자기 수준이 150쯤인 사람은 **10문항 넘게 풀어야**
그 근처에 도달했습니다.

> **비유 — 시력검사표.**
> 시력검사는 **큰 글씨부터** 시작합니다. 처음부터 제일 작은 줄을 들이밀지 않습니다.
> 그리고 큰 줄에서 작은 줄로 성큼성큼 내려가다가, 헷갈리기 시작하는 근처에서 한 줄씩 세밀하게 봅니다.
>
> 수도꼭지로 물 온도 맞추는 것과도 같습니다. 처음엔 크게 돌리고, 적당해지면 조금씩 돌립니다.
> 처음부터 1도씩 돌리면 원하는 온도까지 한참 걸립니다.

**후**

```ts
export const STAIRCASE = {
  /**
   * 초기 cent 격차.
   * 누구나 들리는 쉬운 값에서 시작해 하강한다.
   * (이전 50은 반음의 절반이라 초심자가 첫 문제부터 틀리는 원인이었음)
   */
  INITIAL_CENTS: 200,
  MIN_CENTS: 10,
  MAX_CENTS: 300,
  /** 난이도 하강 트리거 (연속 정답 수) — 2-down-1-up */
  STREAK_THRESHOLD: 2,

  /**
   * 가변 스텝 표 — 반전이 쌓일수록 조정 폭을 좁힌다.
   *
   * 초반엔 크게 움직여 빨리 수렴시키고, 자기 수준 근처에서는 미세 조정한다.
   * `fromReversal` 이상의 반전 횟수에서 해당 `step`을 적용한다.
   */
  STEP_SCHEDULE: [
    { fromReversal: 0, step: 50 },
    { fromReversal: 2, step: 20 },
    { fromReversal: 4, step: 10 },
  ],

  THRESHOLD_DISCARD_REVERSALS: 2,
  THRESHOLD_MIN_REVERSALS: 4,
} as const;
```

`STEP_DOWN` / `STEP_UP` 두 상수는 **삭제**하고 `STEP_SCHEDULE`로 대체했습니다.

```ts
/**
 * 반전 횟수에 대응하는 조정 폭을 구합니다.
 *
 * STEP_SCHEDULE에서 `fromReversal <= reversalCount`인 항목 중 마지막 값을 씁니다.
 */
private static stepForReversals(reversalCount: number): number {
  // `as const` 때문에 리터럴 타입으로 좁혀지므로 number로 명시한다
  let step: number = STAIRCASE.STEP_SCHEDULE[0].step;
  for (const entry of STAIRCASE.STEP_SCHEDULE) {
    if (reversalCount >= entry.fromReversal) {
      step = entry.step;
    }
  }
  return step;
}
```

## ② P1-1 — 반전 기반 변별 역치

### 왜 고쳤나

기존 대표 지표 `minCentsAchieved`는 **세션 중 도달한 최솟값 하나**였습니다.
그런데 이 게임은 높음/낮음 둘 중 하나라 **찍어도 50% 확률로 맞습니다.**
운 좋게 두 번 연속 찍어 맞히면 실력과 무관하게 기록이 뚝 떨어집니다. **한 번의 운이 기록으로 남는 구조**였습니다.

> **비유 — 시력검사.**
> 검사에서 한 번 운 좋게 읽어낸 **가장 작은 글씨**를 시력으로 적지 않습니다.
> 큰 줄과 작은 줄을 오르내리며 "겨우 보이는 경계"를 여러 번 찾고, **그 지점들을 평균**냅니다.
>
> 체중으로 바꿔 말하면 — 일주일 중 **가장 가벼웠던 순간**을 몸무게로 기록하는 대신
> 아침저녁 오르내린 값의 평균을 쓰는 것과 같습니다.

### "반전"이란

난이도가 **내려가다가 올라가거나, 올라가다가 내려간 지점**입니다.
그 사람의 한계선 근처에서만 방향이 바뀌므로, 반전 지점들이 곧 능력의 경계입니다.

```
난이도
 200 ┐
     │ 맞힘
 150 ┤
     │ 맞힘
 100 ┤────── 틀림 → 방향 전환!  ← 반전 ① (100 기록)
     │
 150 ┤────── 맞힘 → 방향 전환!  ← 반전 ② (150 기록)
     │
 100 ┤
  80 ┤────── 틀림 → 방향 전환!  ← 반전 ③ (80 기록)
     │
 100 ┤────── 맞힘 → 방향 전환!  ← 반전 ④ (100 기록)
  80 ┘

초기 2개는 아직 수렴 전이라 버림 → [80, 100] → 역치 = 90
```

### 코드 — `src/training/StaircaseEngine.ts`

**신규 상태**
```ts
/** 반전이 일어난 지점의 cent 값들 (시간순) */
private reversals: number[] = [];
/** 직전 난이도 이동 방향. 아직 움직인 적 없으면 null */
private lastDirection: StepDirection | null = null;
```

**반전 판정 (신규)**
```ts
// 반전 판정 — 격차가 실제로 움직였을 때만
// (MIN/MAX에 걸려 값이 그대로면 방향이 바뀐 것으로 보지 않는다)
if (nextCents !== prev.centsDifference) {
  const direction: StepDirection =
    nextCents < prev.centsDifference ? 'down' : 'up';

  if (this.lastDirection !== null && direction !== this.lastDirection) {
    // 방향이 바뀐 지점의 난이도를 기록한다
    this.reversals.push(prev.centsDifference);
  }
  this.lastDirection = direction;
}
```

**역치 산출 (신규)**
```ts
/**
 * 반전 기반 변별 역치(cent)를 반환합니다.
 *
 * 초기 THRESHOLD_DISCARD_REVERSALS개는 수렴 전 구간이라 버리고,
 * 남은 반전값의 평균을 씁니다. 상승·하강 반전이 균형을 이루도록 **짝수 개**만 사용합니다.
 *
 * @returns 역치(cent). 반전이 부족하면 null
 */
getThreshold(): number | null {
  if (this.reversals.length < STAIRCASE.THRESHOLD_MIN_REVERSALS) {
    return null;
  }

  let used = this.reversals.slice(STAIRCASE.THRESHOLD_DISCARD_REVERSALS);
  if (used.length % 2 === 1) {
    // 가장 오래된 것을 하나 더 버려 짝수를 맞춘다
    used = used.slice(1);
  }
  if (used.length === 0) {
    return null;
  }

  const mean = used.reduce((a, b) => a + b, 0) / used.length;
  return Math.round(mean * 10) / 10;
}
```

> **왜 초기 2개를 버리나?** 시작값 200은 누구에게나 쉽습니다.
> 처음 몇 번의 방향 전환은 "능력의 경계"가 아니라 아직 내려오는 중에 생긴 것입니다.
> 시력검사로 치면 큰 글씨 줄에서 잠깐 헷갈린 것을 시력으로 치지 않는 것과 같습니다.

> **왜 짝수 개만 쓰나?** 반전은 "위로 꺾임"과 "아래로 꺾임"이 번갈아 나옵니다.
> 홀수 개를 평균내면 한쪽 방향이 하나 더 들어가 값이 미세하게 치우칩니다.

## ③ P1-7 — 연속 배지 분리

### 왜 고쳤나

화면의 `🔥 연속: n회` 배지가 **0과 1만 반복**했습니다.
난이도 제어용 카운터와 화면 표시용 숫자가 **같은 변수**였기 때문입니다.
2회 연속 정답으로 난이도를 낮출 때 카운터를 0으로 리셋하는데, 그게 화면 숫자까지 지웠습니다.

> **비유.** 계산기 하나로 장부 합계와 화면 표시를 같이 쓰다가,
> 중간 정산할 때 `C` 버튼을 눌러 화면까지 지워버린 상황입니다.
> 계산은 맞는데 사용자에게 보이는 숫자가 사라집니다.

### 코드 — `src/training/StaircaseEngine.ts`

**전** — 하나의 `streak`이 두 역할

## ④ P1-2 — 평가 모드 실제 분기

### 왜 고쳤나

`🏋️ 훈련` / `📋 평가` 버튼이 있었지만, 코드상 **완전히 똑같이 동작**했습니다.
`SessionManager`가 `mode` 값을 결과에 기록만 하고 아무 분기도 하지 않았습니다.
**이름표뿐인 기능**이었습니다.

특히 문제는 평가 중에도 시행마다 정답을 알려줬다는 점입니다.

> **비유 — 시험.**
> 시험 중에 문제마다 정답을 알려주면, 뒷 문제는 앞에서 배운 걸로 풉니다.
> 그러면 "원래 실력"이 아니라 "배우면서 푼 실력"을 재게 됩니다.
> 그래서 시험은 **끝나고 채점**합니다.
>
> 또 시험은 **문항 수가 정해져 있어야** 점수를 비교할 수 있습니다.
> 어떤 날은 5문제, 어떤 날은 50문제 풀면 두 결과를 나란히 놓을 수 없습니다.

## ⑤ P0-5 — 오디오 클럭 기준 일괄 예약

### 왜 고쳤나

A 소리와 B 소리를 **각각 따로** 예약하고 있었습니다.
B는 `setTimeout` 콜백 안에서 "지금 재생"으로 시작했는데, 그 사이 JS 스레드가 바쁘면
A→B 간격이 수십 ms 흔들립니다. 흔들린 간격은 음고 대신 **시간 단서**로 쓰일 수 있습니다.

> **비유 — 요리 타이머.**
> "계란 3분" 누르고, 잠시 뒤 "면 5분"을 누르면 그 사이 몇 초가 어긋납니다.
> 두 개가 정확히 맞물려야 한다면 **동시에 세팅**해야 합니다.
>
> 지휘자로 바꿔 말하면 — 두 연주자에게 각각 "지금부터 1.5초 뒤 시작"이라고 따로 말하면
> 말하는 사이 시간이 흘러 어긋납니다. 한 번에 악보를 주고 같은 메트로놈에 맞추게 해야 합니다.

### 코드 — `src/audio/AudioEngine.ts` (신규 메서드)

```ts
/**
 * 여러 톤을 **하나의 오디오 클럭 기준점**에 맞춰 한 번에 예약합니다.
 *
 * 톤마다 `playTone`을 따로 부르면 호출 시점의 `currentTime`이 각각 달라지고,
 * 그 사이에 낀 JS 타이머·마이크로태스크 지연이 자극 간 간격(ISI)에 섞입니다.
 * Android에서 JS 스레드가 바쁘면 수십 ms까지 흔들릴 수 있고,
 * 흔들린 간격은 음고 대신 **시간 단서**로 작동할 수 있습니다.
 */
async playSequence(
  tones: readonly { freq: number; offset: number; duration: number }[],
  mode: SoundMode,
): Promise<boolean> {
  const ready = await this.ensureRunning();
  if (!ready || !this.ctx) return false;

  const ctx = this.ctx;
  // 기준점을 한 번만 읽는다 — 이 값이 시퀀스 전체의 시간 원점이 된다
  const base = ctx.currentTime;

  for (const tone of tones) {
    const startTime = base + tone.offset;
    if (mode === 'wave') {
      this.playSineTone(ctx, tone.freq, startTime, tone.duration);
    } else {
      this.playVoiceTone(ctx, tone.freq, startTime, tone.duration);
    }
  }

  return true;
}
```

기존 `playTone`은 이 메서드에 위임하도록 바꿔 **호출부 호환을 유지**했습니다.
```ts
async playTone(freq, startTimeOffset, duration, mode): Promise<void> {
  await this.playSequence([{ freq, offset: startTimeOffset, duration }], mode);
}
```

### 코드 — `app/training.tsx`

**전** — B를 타이머 안에서 "지금 재생"

```tsx
// 톤마다 따로 예약하면 그 사이의 JS 지연이 A→B 간격에 섞인다.

```

## ⑥ P0-6 — 앱 이탈 시 라운드 폐기

### 왜 고쳤나

앱을 백그라운드로 보내도 **타이머는 계속 돌았습니다.**
전화를 받고 돌아오면 소리는 하나도 못 들었는데 답변 버튼만 활성화돼 있었습니다.
찍을 수밖에 없고, **그 찍은 답이 기록에 남았습니다.**

> **비유 — 듣기 평가 중 전화.**
> 듣기 평가를 보는 중에 전화가 왔는데, 시험지는 계속 넘어가는 상황입니다.
> 못 들은 문제에 아무거나 찍은 게 그대로 성적에 들어갑니다.

### 코드 — `src/training/trainingFlow.ts`

**전**
```ts
export type GameState = 'idle' | 'playing' | 'waiting' | 'answered';
```

**후**
```ts
export type GameState =
  | 'idle'
  | 'playing'
  | 'waiting'
  | 'answered'
  | 'interrupted';
```

신규 규칙
```ts
/**
 * 앱 이탈·통화 등으로 라운드를 버려야 하는 상태인가.
 *
 * 재생 중이거나 답변 대기 중이었다면 그 라운드는 신뢰할 수 없습니다.
 * 이미 답한('answered') 라운드나 시작 전('idle')은 영향이 없습니다.
 */
export function shouldAbortOnInterrupt(state: GameState): boolean {
  return state === 'playing' || state === 'waiting';
}
```

`isReplayPress`에 설명 보강
```ts
/**
 * 'interrupted'에서 false인 이유: 자극을 일부만 들었을 수 있어
 * 같은 문제를 다시 주면 부분 노출이 단서로 남습니다. 새 문제가 안전합니다.
 */
```

버튼 문구 추가
```ts
interrupted: '▶️ 새 문제로 다시 듣기 (A → B)',
```

### 코드 — `src/training/SessionManager.ts` (신규 메서드)

```ts
/**
 * 진행 중이던 라운드를 폐기합니다. (앱 이탈·통화 등으로 자극을 놓친 경우)
 *
 * 시행으로 기록되지 않습니다. 답변을 받기 전 상태로 되돌릴 뿐입니다.
 */
abortRound(): void {
  this.responseWindowOpenedAt = 0;
  this.replayCount = 0;
}
```

### 코드 — `app/training.tsx` (신규 effect)

```tsx
/**
 * 앱 이탈·통화 인터럽션 처리 (P0-6)
 *
 * 백그라운드로 가도 타이머는 계속 돌기 때문에, 소리를 못 들은 채
 * 답변 버튼만 활성화된 상태로 돌아오게 됩니다. 그 라운드는 폐기합니다.
 */
useEffect(() => {
  const subscription = AppState.addEventListener('change', (nextState) => {
    if (nextState === 'active') return;

    setGameState((prev) => {
      if (!shouldAbortOnInterrupt(prev)) return prev;

      timersRef.current.forEach(clearTimeout);
      timersRef.current = [];
      setActiveSound('none');
      sessionManager.abortRound();
      return 'interrupted';
    });
  });

  return () => subscription.remove();
}, [sessionManager]);
```

사용자에게 상황을 알립니다.
```tsx

  <View style={[styles.noticeCard, styles.noticeCardWarn]}>
    <Text style={styles.noticeText}>
      소리를 놓쳐 이번 문제는 기록하지 않았습니다.{'\n'}
      새 문제로 다시 시작해 주세요.
    </Text>
  </View>

```

> **왜 같은 문제를 다시 주지 않나?** 소리를 **일부만** 들었을 수 있습니다.
> A는 들었고 B만 놓쳤다면, 같은 문제를 다시 줄 때 A의 기억이 힌트가 됩니다.
> 그 시행은 다른 시행과 조건이 달라져 버립니다. 새 문제가 안전합니다.

| 연속 | 검증 없음 | 표시용 `streak`과 `stepCounter` 분리 검증 |
| 역치 | 없음 | 반전 기록·평균·최소 반전 수 |
