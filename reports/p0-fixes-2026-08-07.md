## P0-1. 답변 중복 제출 차단

**증상.** 답변 후 상태가 `'answered'`인데 답변 버튼이 활성이고 핸들러도 통과했습니다.
피드백으로 정답을 확인한 뒤 같은 버튼을 반복 탭하면 시행 수·정답 수·연속이 무제한으로 누적되고
난이도(cent)도 계속 내려갔습니다.

**수정.**

```diff
- if (gameState !== 'waiting' && gameState !== 'answered') return;
+ if (gameState !== 'waiting') return;
```
```diff
- disabled={gameState === 'playing' || gameState === 'idle'}
+ disabled={gameState !== 'waiting'}
```

`SessionManager.submitAnswer()`에서도 답변 직후 `responseWindowOpenedAt = 0`으로 닫아 이중 방어를 두었습니다.

**상태 경로 확인.** `'answered'`에서 다시 `'waiting'`으로 가는 경로는
`runPlaybackSequence()` 하나뿐이고, 이 함수는 `handleNextRound`(= `prepareRound` 동반)와
`handleReplay`(= `gameState === 'waiting'` 요구)에서만 호출됩니다.
따라서 답변 후에는 **새 라운드를 뽑지 않고서는** 답변 창이 다시 열리지 않습니다.

## P0-2. 다시 듣기 / 다음 문제 분리

**증상.** 재생 버튼이 상태와 무관하게 항상 `sessionManager.prepareRound()`를 호출했고,
`StaircaseEngine.prepareRound()`는 매번 `Math.random() > 0.5`로 방향을 새로 정했습니다.
결과적으로 "다시 듣기"가 **정답을 재추첨**했고, 답하지 않고 재생만 반복해 어려운 문제를 회피할 수 있었습니다.

**수정.** 재생 시퀀스를 라운드 결정과 분리했습니다.

```
runPlaybackSequence(baseFreq, targetFreq)   재생만 담당. 추첨하지 않음
  ├─ handleNextRound()   prepareRound() 호출 → 새 방향   (idle / answered)
  └─ handleReplay()      getStaircaseState() 사용 → 방향 유지  (waiting 전용)

handlePlayPress = gameState === 'waiting' ? handleReplay : handleNextRound
```

버튼 문구도 `PLAY_BUTTON_LABEL` 상수로 상태별 분기했습니다.

| 상태 | 문구 |
|------|------|
| `idle` | ▶️ 소리 듣기 (A → B) |
| `playing` | 🔊 소리 감상 중... |
| `waiting` | 🔁 다시 듣기 (A → B) |
| `answered` | ▶️ 다음 소리 듣기 (A → B) |

**부가.** 다시 듣기 횟수를 `TrialRecord.replayCount`(optional)로 기록합니다.
`prepareRound()`에서 0으로 초기화되므로 라운드 단위 값이며, 구버전 저장 데이터와 호환됩니다.

## P0-3. 반응 시간 측정 시점 이동

**증상.** `prepareRound()`에서 `roundStartTime`을 잡아, A(1.0s) + 갭(0.5s) + B(1.0s) = **2500ms가 항상 포함**됐습니다.
통계 화면의 "평균 반응 시간"은 구조적으로 3000ms 미만이 나올 수 없었습니다.

**수정.** `roundStartTime` → `responseWindowOpenedAt`으로 교체하고, 측정 시작을 답변 가능 시점으로 옮겼습니다.

```
prepareRound()          responseWindowOpenedAt = 0  (측정 안 함)
  → A 재생 → 갭 → B 재생
  → openResponseWindow()  ← 여기서부터 측정 (setGameState('waiting')와 같은 타이머)
  → submitAnswer()        RT = now - responseWindowOpenedAt
```

다시 듣기로 재재생하면 `openResponseWindow()`가 다시 호출되어 **마지막 재생 종료 시점** 기준으로 갱신됩니다.
창이 열리기 전 답변이 들어오면 `0`을 기록하도록 가드를 두었습니다(현재 상태 게이트상 도달 불가).

**주의.** 이 변경으로 기존 데이터와 새 데이터의 반응 시간 단위 의미가 달라집니다.
누적 평균을 비교할 때 섞이지 않게 해야 합니다.

## P0-4. 톤 엔벨로프 서스테인 복구

**증상.** 두 번째 램프의 **종점**이 `duration - RELEASE_TIME`이었습니다.

```ts
gain.gain.exponentialRampToValueAtTime(0.4, startTime + 0.05);      // Attack 종료
gain.gain.exponentialRampToValueAtTime(0.001, startTime + 0.95);    // ← 0.05s부터 여기까지 감쇠
```

Web Audio의 램프는 **직전 자동화 이벤트 시점**부터 시작하므로,
0.05s → 0.95s 구간 내내 0.4에서 0.001로 약 52dB 감쇠했습니다. 서스테인 구간이 없었습니다.
문서상 1.0초 톤이지만 체감 길이는 수백 ms였고, 자극 길이가 짧을수록 음고 변별이 어려우므로
**역치가 실제보다 나쁘게 측정**됐습니다.

**수정.** Release 시작점을 `setValueAtTime` 앵커로 고정해 평탄 구간을 만들었습니다.

```ts
const { attackEnd, releaseStart, end } = this.envelopeTimes(startTime, duration);
gain.gain.setValueAtTime(0.001, startTime);
gain.gain.exponentialRampToValueAtTime(peak, attackEnd);   // Attack
gain.gain.setValueAtTime(peak, releaseStart);              // Sustain 앵커 (이게 핵심)
gain.gain.exponentialRampToValueAtTime(0.001, end);        // Release
```

`envelopeTimes()`는 `duration`이 Attack+Release보다 짧아도 구간 순서가 뒤집히지 않도록 보정합니다.
voice 모드도 동일 구조로 맞췄고(Attack만 0.1s 유지), 게인 상수 `0.4` / `0.3`은 `AUDIO`로 옮겼습니다.

**결과.** 1.0초 톤 기준 서스테인 900ms 확보(전체의 90%), Release가 톤 끝(1.0s)에서 종료.

| 항목 | 이전 데이터의 문제 |
