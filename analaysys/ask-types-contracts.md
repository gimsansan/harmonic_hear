# 타입·계약 파악 — 질문 요령 (범용)

> **역할**: 파일을 열고 AI에게 물을 때, **타입 정의부터 훑지 않고** 이 경계에서 무엇을 주고받기로 했는지를 빨리 그리는 법. React / React Native / 웹·앱(주로 TypeScript) 공통.
> **자매 문서**: [`ask-file-behavior.md`](./ask-file-behavior.md) 화면(#1), [`ask-data-flow.md`](./ask-data-flow.md) 데이터(#2), [`ask-state-management.md`](./ask-state-management.md) 상태(#3), [`ask-error-handling.md`](./ask-error-handling.md) 에러(#4).
> **관계**: 이 문서는 파악의 **5번 축(타입·계약)**이다. 다른 축과 별개로, 한 번에 하나씩 본다.
> **표기**: 계약은 시그니처로 `이름(입력: 타입) → (출력: 타입)`. 이어지는 화면 `[ ]`, 데이터 `{ }`, 상태 `( )@소유자`, 실패 `! !`는 자매 문서와 동일.
> **에이전트 실행 시**: 축을 시작하기 전에 대상 파일 목록을 고정하고, 축마다 그 목록을 전부 훑는다. 열지 못한 파일은 결과 문서에 "안 읽음"으로 남긴다. 여러 축을 한 번의 조사로 합치지 말 것.
> 코드 동작의 정본(定本)이 아님. **질문 형식**만 다룬다.

---

## 0. 한 줄 + 왜

타입 정의를 붙여 「이 타입 뭐냐」부터 물으면 느리다.
**이 경계에서 무엇을 받기로 하고 → 무엇을 주기로 했고 → 그 약속이 실제와 맞나**를 먼저 그리게 하면, 다음 질문이 갈린다.

### 왜 타입 정의부터 물으면 느린가

- **이유 1 — 경계가 안 잡힌다.**
  타입 하나만 보면, 그게 **누구와 누구 사이의 약속**인지(어느 컴포넌트가 받고, 어느 API가 주는지)가 안 보인다. 타입은 경계에서 의미가 산다.

- **이유 2 — 컴파일타임과 런타임의 간극.**
  타입은 **믿기로 한 약속**일 뿐이다. 외부 데이터(API 응답)는 선언과 실제가 다를 수 있고, `any`나 강제 단언(`as`)으로 약속을 우회하면 **실제로 깨져도 타입 검사는 통과**한다. (컴파일타임 = 타입 검사 시점, 런타임 = 실행 시점)

- **이유 3 — 선택 값·null이 안 열린다.**
  `?`나 `| null`이 붙은 값을 안 열어보고 그냥 쓰면 런타임에서 터진다. 타입만 훑으면 이걸 놓친다.

그래서 **계약**(`이름(입력: 타입) → (출력: 타입)`, 그리고 "약속 vs 실제")을 먼저 그리게 한다.

---

## 데이터 흐름(#2)과 무엇이 다른가

| 축             | 데이터의 무엇을 보나                                                     |
| -------------- | ------------------------------------------------------------------------ |
| #2 데이터 흐름 | 데이터가 **어디로 가나** (경로)                                          |
| #5 타입·계약   | 그 데이터의 **모양이 무엇으로 약속됐나, 약속이 실제와 맞나** (형태·검증) |

---

## 사용법 (순서)

```
파일을 열었다
        │
        ▼
① 이 파일의 타입이 어떤 경계의 약속인지 모름
        │   →  §1 "첫 질문" 복붙   →  AI가 4종류 중 하나로 답
        ▼
② 종류가 정해졌다
        │   →  §2 에서 그 종류의 질문만 골라 씀
        ▼
③ 두 번째부터: 특정 타입·함수 코드를 붙여 묻는다
            →  §3 "타입을 붙여 물을 때"
```

- **경계 1개만** 따라간다(예: 이 컴포넌트의 props 하나). 파일의 모든 타입을 한 번에 묻지 말 것.

---

## 1. 첫 질문 (어떤 경계의 약속인지 모를 때) — 복붙

```
이 파일의 타입은 어떤 경계의 약속인가? 아래에 가까운가?
1. 컴포넌트 계약 (props: 무엇을 받나, 필수/선택, 기본값)
2. 함수 계약 (파라미터 → 반환값 시그니처)
3. 데이터 계약 (외부: API 응답·저장소 스키마 — 내가 통제 못 하는 모양)
4. 공유 타입 (여러 곳이 쓰는 정의: interface/type, enum, 도메인 모델)

고른 뒤:
1이면 무엇을 받나(필수/선택/기본값). 안 넘기면 어떻게 되나?
2이면 입력 → 출력 한 줄. 선택 값·null이 섞였나?
3이면 약속된 모양은 무엇. 실제 응답이 다를 때 검증하나, 그냥 믿나?
4이면 누가 이 타입을 쓰나. 바뀌면 어디가 다 영향받나?

경계 1개만 따라가. 모든 타입 나열하지 마.
```

한 번에 「타입 다 설명해」보다 **경계 종류를 먼저** 고르게 한다.

---

## 2. 종류가 정해진 뒤

### 1) 컴포넌트 계약 (props)

```
이 컴포넌트가 무엇을 받나. Comp(props: 타입) → 렌더
어떤 게 필수고 어떤 게 선택(?)이며 기본값은 무엇인가?
필수인데 안 넘기거나, 선택인데 안 열고 쓰면 어떻게 되나?
```

- **볼 자리**: props 타입/interface(`*Props`), 구조분해 기본값, 선택 표시(`?`).
- **핵심**: 필수/선택/기본값 세 가지를 구분한다. 선택 값을 안 열고 쓰는 곳이 위험.

### 2) 함수 계약 (시그니처)

```
입력 → 출력 한 줄. fn(입력: 타입) → (출력: 타입)
선택 파라미터·null 반환이 섞였나?
같은 함수가 입력에 따라 다른 모양을 반환하나(오버로드/유니온)?
```

- **볼 자리**: 파라미터 타입, 반환 타입 애노테이션, 제네릭(`<T>`, 여러 타입에 두루 쓰는 틀).
- **핵심**: 반환이 `T | null | undefined`면, 받는 쪽이 열어 쓰는지 확인.

### 3) 데이터 계약 (외부)

```
약속된 모양은 무엇인가(API 응답 타입)?
실제 응답이 그 타입과 다를 수 있나. 다르면 어떻게 아나?
검증하나(런타임 검사), 아니면 타입만 믿고 as로 단언하나?
```

- **볼 자리**: 응답 타입(`*Response`, `*Dto`), fetch 결과에 붙인 타입, 강제 단언(`as`), 런타임 검증 라이브러리(예: Zod) 스키마.
- **핵심**: 외부 데이터는 **내가 통제 못 한다.** 타입 선언은 약속일 뿐이므로, 검증 없이 믿는 지점이 취약점.

### 4) 공유 타입

```
이 타입을 누가 쓰나(어느 파일·컴포넌트들)?
이걸 바꾸면 어디가 다 영향받나?
같은 개념을 두 타입으로 중복 정의하진 않았나?
```

- **볼 자리**: `types.ts` / `*.d.ts`, `enum`, 도메인 모델(`*Model`), export된 `type`/`interface`.
- **핵심**: 공유 타입은 **원본 하나**여야 한다. 중복 정의는 어긋남의 원인.

---

## 3. 타입을 붙여 물을 때 (두 번째부터)

파일의 **모든** 타입에 설명을 요청하지 말 것. 경계 1개만 좁혀서 묻는다.

| 상황                | 질문                                                   |
| ------------------- | ------------------------------------------------------ |
| 컴포넌트 props      | `Comp(props: 타입) → 렌더`. 필수/선택/기본값만         |
| 함수 시그니처       | `fn(입력: 타입) → (출력: 타입)` 한 줄. null 반환 있나? |
| 외부 데이터 타입    | 약속된 모양 vs 실제. 검증하나, `as`로 믿나?            |
| 이 타입을 누가 쓰나 | 이 타입에 의존하는 곳 **전부**. 바꾸면 어디가 깨지나   |
| 두 타입이 헷갈림    | `A` vs `B` 무엇이 다른가. 시그니처 두 줄               |

> 세 번째 행이 §0 "이유 2"에 대응한다. `as` 단언이나 `any`가 보이면, 약속을 우회한 지점이다.

---

## 4. 하지 말 것

- **`any` / 강제 단언(`as`)으로 약속 우회**하기 (타입은 통과, 런타임은 깨짐)
- **외부 데이터(API)를 검증 없이 타입만 믿기**
- **선택 값(`?`)·null을 안 열고** 바로 쓰기
- 같은 개념을 **여러 타입으로 중복 정의**하기 (원본 둘 → 어긋남)
- 파일의 **모든 타입을 한 번에 나열** 요청하기 (한 경계의 계약만)
- 타입 축과 다른 축을 **한 질문에 섞기** (축은 하나씩)

---

## 5. 경로 감 (힌트, 단정 아님)

| 흔한 표시                                         | 보통                 |
| ------------------------------------------------- | -------------------- |
| `*Props` `interface *Props` props 구조분해        | 1. 컴포넌트 계약     |
| 함수 시그니처 `: ReturnType` 제네릭 `<T>`         | 2. 함수 계약         |
| `*Response` `*Dto` `as` 단언 검증 스키마(예: Zod) | 3. 데이터 계약(외부) |
| `types.ts` `*.d.ts` `enum` `*Model` export된 타입 | 4. 공유 타입         |

이름은 힌트일 뿐 사실이 아니다. 감이 틀려도 §1이 바로잡는다. 파일은 읽고 나서 고른다.

---

## 6. 다른 축과 이어 보기 (선택)

계약은 경계마다 얹힌다. 다른 축의 화살표 위에 "무슨 타입으로 약속됐나"를 붙인다.

```
{서버 API} → (약속: Item[]) → 검증? → [목록 화면]        (데이터 경계: 약속 vs 실제)
<ItemCard>(props: {item: Item}) → 렌더                   (컴포넌트 경계)
(선택된 항목: Item | null)@목록화면                        (상태에 얹힌 계약: null 열어 쓰기)
```

`( )` 시그니처·계약, `[ ]` 화면, `{ }` 데이터, `( )@소유자` 상태. 한 번에 하나씩 그린 지도를 나중에 이렇게 포갠다.
