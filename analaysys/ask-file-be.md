# 파일 동작 파악 — 질문 요령 (범용)

> **역할**: 파일을 열고 AI에게 물을 때, **함수부터 파지 않고** 동작을 빨리 그리는 법. React / React Native / 웹·앱 화면 코드에 공통.
> **이 저장소 전용 예**: [`ask-app-behavior.md`](./ask-app-behavior.md)
> **표기**: 화면·단계는 `[목록]` `[설정]`처럼 **이름**으로 적는다. 동그라미 숫자(①②③ 모양)로 화면을 매기지 말 것 — 표시가 잘 안 보인다.

> **에이전트 실행 시**: 축을 시작하기 전에 대상 파일 목록을 고정하고, 축마다 그 목록을 전부 훑는다. 열지 못한 파일은 결과 문서에 "안 읽음"으로 남긴다. 여러 축을 한 번의 조사로 합치지 말 것.

코드 동작의 정본(定本)이 아님. **질문 형식**만 다룬다.

---

## 0. 한 줄 + 왜

코드 조각을 붙여 「이 함수 하는 일」부터 물으면 느리다.
**이 파일이 무슨 역할인지**를 먼저 고르게 하면, 다음 질문이 갈린다.

### 왜 함수부터 물으면 느린가

- **이유 1 — 어느 화면인지 감이 안 온다.**
  함수만 물으면 "이 함수는 X를 한다"는 답은 받는다. 그런데 그게 **앱의 어느 화면에서 벌어지는 일인지**가 안 잡힌다. 답을 받아도 앱 그림이 안 그려진다.

- **이유 2 — 같은 동작이 여러 화면에서 일어난다.**
  하나의 함수가 한 화면이 아니라 **여러 화면에서 호출**될 수 있다. 함수만 보면 "어디에서 쓰이나"가 하나로 안 잡힌다. 화면 지도를 먼저 그려야 그 동작이 **어디어디서** 일어나는지 화살표로 다 드러난다.

그래서 **화면 지도**(`[화면] --동작--> [화면]`)를 먼저 그리게 한다.

---

## 사용법 (순서)

이 문서는 아래 순서로 쓴다. 위에서부터 필요한 단계만 골라 복붙한다.

```
파일을 열었다
        │
        ▼
① 이 파일이 무슨 종류인지 모름
        │   →  §1 "첫 질문" 복붙   →  AI가 4종류 중 하나로 답
        ▼
② 종류가 정해졌다
        │   →  §2 에서 그 종류의 질문만 골라 씀
        ▼
③ 두 번째부터: 특정 함수 코드를 붙여 묻는다
            →  §3 "함수를 붙여 물을 때"
```

- **처음 여는 파일**이면 §1부터. 파일만 지정해도 된다(코드를 다 붙일 필요 없음).
- **종류를 이미 안다**면 §1을 건너뛰고 §2에서 해당 종류로 바로 간다.
- **함수 하나가 헷갈린다**면 그때 §3 방식으로 코드를 붙인다.
- §4는 매번 피할 것, §5는 파일 이름으로 종류를 미리 짐작하는 힌트다.

## 1. 첫 질문 (파일 종류를 모를 때) — 복붙

```
이 파일은 아래에 가까운가?
1. 화면·단계를 갈아끼움 (페이지, 모달, 마법사, 탭)
2. 데이터를 넣거나 읽음 (API, 저장소, 서버 상태)
3. 숫자를 그림 (차트, 대시보드, 진행률)
4. 계산만 (순수 함수, 포맷, 유효성)

고른 뒤:
1이면 [화면 이름] --동작--> [화면 이름]
2이면 언제 1건이 오가나. 안 보내는/안 넣는 경우는?
3이면 무슨 숫자 1개인지. 없는 값은 안 그리나?
4이면 입력 → 출력 한 줄.

동그라미 숫자로 화면 번호 매기지 마.
```

한 번에 「지도 그려」보다 **종류를 먼저** 고르게 하는 것이 핵심이다.

## 2. 종류가 정해진 뒤

### 1) 화면·단계를 갈아끼움

파일 전체를 **한 번**에 보고 묻는다:

```
이 파일에서 사용자가 보는 화면이 어떻게 바뀌나.
[화면 이름] --동작--> [화면 이름] 만.
함수 이름은 화살표 옆에만.
동그라미 숫자 쓰지 마.
```

React 예 (한 페이지 안에서 `step` / `view` 상태로 화면을 바꾸는 경우):

```
[목록] --항목 누름--> [상세] --수정--> [편집]
[목록] --추가--> [작성]
[상세] --뒤로--> [목록]
[편집] --저장--> [상세]
[편집] --취소--> [상세]
```

라우터를 쓰면 파일 하나가 곧 한 화면일 수 있다. 그때는 **이 페이지에서 모달·패널이 어떻게 열리는지**만 그리면 된다. 라우트 이동은 `[이 페이지] --링크--> [다른 라우트]` 한 줄로 적는다.

**볼 자리**: `if` / `switch(phase)` / 이른 `return <다른JSX>`.
그 분기가 어떤 화면을 보여줄지 결정한다. `useState` setter를 나열하는 것부터 묻지 말 것.

같은 파일의 `onClick`을 하나씩 「하는 일」로 따로 묻지 말 것. 지도 한 장에 다 이어진다.

### 2) 데이터를 넣거나 읽음

```
언제 요청/저장이 나가나. 실패·빈 값·미완료는?
읽는 쪽이 필터하나, 받은 것 전부 보여 주나?
```

React 예: `useQuery` / `fetch` / Context / 로컬 스토리지 훅.

### 3) 숫자를 그림

```
무슨 숫자 1개를 그리나.
데이터가 부족하면? 가짜 점을 넣나, 차트만 숨기나?
```

### 4) 계산만

```
입력 → 출력 한 줄. 화면 이야기 하지 마.
```

## 3. 함수를 붙여 물을 때 (두 번째부터)

화면 파일의 **모든** 함수에 지도를 요청하지 말 것. 필요한 함수만 좁혀서 묻는다.

| 상황                         | 질문                                                                         |
| ---------------------------- | ---------------------------------------------------------------------------- |
| 화면을 바꾸는 함수           | 이 함수가 **바꾸는 화면만** `[이름] --동작-->`                               |
| 상태만인지 모름              | 화면을 바꾸나, 상태만 바꾸나? 바꾸면 화살표, 아니면 「화면 이동 없음」       |
| 한 함수가 여러 화면에서 쓰임 | 이 함수를 호출하는 화면 **전부**. `[A]--f-->[B]`, `[C]--f-->[D]` 처럼 줄마다 |
| 두 함수가 헷갈림             | `A` vs `B` 무엇이 다른가. 화살표 두 줄                                       |

> 세 번째 행이 §0 "이유 2"에 대응한다. 같은 함수가 여러 화면에서 불릴 수 있으므로, "이 함수 하는 일"이 아니라 **"어느 화면들에서 부르나"**를 화살표로 받는다.

코드를 붙여 묻는 방식은 여기에 해당한다. 파일 첫 질문(§1)은 파일만 지정해도 된다.

---

## 4. 하지 말 것

- 함수 본문의 `setState` / setter 표부터 요청하기
- 화면을 동그라미 숫자로 매기기
- 「시각적으로 단계적 화면」만 말하고 이름 형식(`[화면 이름]`)을 안 주기
- 훅·유틸·차트 파일에 「화면 갈아끼움 지도」를 요청하기

「시각적으로… 이해하기 쉽겠어」라는 요청은 **화면 파일에는 거의 충분**하다. 다만 표시가 안 보이는 문제를 막으려면 `[화면 이름] --동작-->` 형식을 함께 적어 준다.

---

## 5. 경로 감 (힌트, 단정 아님)

| 흔한 이름                                      | 보통      |
| ---------------------------------------------- | --------- |
| `*Page` `*Screen` `*Tab` `*Layout` 라우트 파일 | 1. 화면   |
| `*api*` `*store*` `*service*` `use*Query`      | 2. 데이터 |
| `*Chart*` `*Dashboard*` `*Stats*`              | 3. 숫자   |
| `*util*` `*lib*` `*parser*` `*validate*`       | 4. 계산   |

이름은 힌트일 뿐 사실이 아니다. 감이 틀려도 §1이 바로잡는다. 파일은 읽고 나서 고른다.
