# 데이터 흐름 파악 — 질문 요령 (범용)

> **역할**: 파일을 열고 AI에게 물을 때, **함수부터 파지 않고** 데이터가 어디서 나서 어디로 가는지를 빨리 그리는 법. React / React Native / 웹·앱 공통.
> **자매 문서**: [`ask-file-behavior.md`](./ask-file-behavior.md) — 화면 흐름 축(#1).
> **관계**: 이 문서는 파악의 **2번 축(데이터 흐름)**이다. 화면 축과 별개로, 한 번에 하나씩 본다.
> **표기**: 데이터 지점은 `{서버 API}` `{캐시}` `{로컬 저장소}`처럼 **중괄호 `{ }`**. 화면은 자매 문서와 같이 대괄호 `[ ]`. 두 축을 포개면 `{서버 API} --목록--> [목록 화면]`처럼 한 줄로 이어진다.
> **에이전트 실행 시**: 축을 시작하기 전에 대상 파일 목록을 고정하고, 축마다 그 목록을 전부 훑는다. 열지 못한 파일은 결과 문서에 "안 읽음"으로 남긴다. 여러 축을 한 번의 조사로 합치지 말 것.

코드 동작의 정본(定本)이 아님. **질문 형식**만 다룬다.

---

## 0. 한 줄 + 왜

코드 조각을 붙여 「이 함수 하는 일」부터 물으면 느리다.
**이 데이터 1건이 어디서 나서 → 어디를 거쳐 → 어디로 가나**를 먼저 그리게 하면, 다음 질문이 갈린다.

### 왜 함수부터 물으면 느린가

- **이유 1 — 데이터 1건의 경로가 안 잡힌다.**
  함수만 물으면 "이 함수는 데이터를 가공한다"는 답은 받는다. 그런데 그 데이터가 **어디서 와서 어디로 가는지**가 안 보인다. 조각만 알고 흐름은 모른다.

- **이유 2 — 실패·빈 값·로딩이 답에서 빠진다.**
  함수 하나만 물으면 대개 **성공한 경우**만 설명된다. 실무에서 사고는 실패·빈 값·로딩·미완료에서 난다. 경로 전체를 물어야 각 상태가 무엇을 내보내는지 드러난다.

- **이유 3 — 진짜 출처가 어디인지 흐려진다.**
  같은 데이터를 서버·캐시·로컬이 각각 들고 있을 수 있다. **원본(진짜 출처, source of truth)**이 어디냐를 정하지 않으면, 어느 값을 믿어야 할지 모른다.

그래서 **데이터 경로**(`{출처} --데이터--> {도착}`)를 먼저 그리게 한다.

---

## 사용법 (순서)

```
파일을 열었다
        │
        ▼
① 이 파일이 데이터로 무엇을 하는지 모름
        │   →  §1 "첫 질문" 복붙   →  AI가 4종류 중 하나로 답
        ▼
② 종류가 정해졌다
        │   →  §2 에서 그 종류의 질문만 골라 씀
        ▼
③ 두 번째부터: 특정 함수 코드를 붙여 묻는다
            →  §3 "함수를 붙여 물을 때"
```

- **처음 여는 파일**이면 §1부터. 파일만 지정해도 된다.
- **종류를 이미 안다**면 §2에서 바로 시작한다.
- **데이터 1종류(또는 1건)만** 따라간다. 전체 스키마를 한 번에 묻지 말 것.

---

## 1. 첫 질문 (파일이 데이터로 뭘 하는지 모를 때) — 복붙

```
이 파일은 데이터로 무엇을 하나? 아래에 가까운가?
1. 가져옴 (읽기: 요청, 구독, 조회)
2. 보냄 (쓰기: 저장, 전송, 생성/수정/삭제)
3. 담아둠 (보관: 저장소, 컨텍스트, 캐시, 로컬 저장소)
4. 바꿈 (변형: 정규화, 선택, 파생값 계산)

고른 뒤:
1이면 언제 나가나(트리거). 실패·로딩·빈 값 각각 무엇을 내보내나?
2이면 언제 보내나. 성공/실패 후 무엇을 갱신하나? 중복 전송은 막나?
3이면 진짜 출처가 여기냐, 서버냐? 언제 갱신되고 누가 읽나?
4이면 입력 → 출력 한 줄. 원본을 건드리나?

데이터 1종류만 따라가. 전체 스키마 나열하지 마.
```

한 번에 「데이터 전부 설명해」보다 **종류를 먼저** 고르게 한다.

---

## 2. 종류가 정해진 뒤

### 1) 가져옴 (읽기)

```
이 데이터 1건이 어디서 오나. {출처} --데이터--> {도착}
언제 요청이 나가나(화면 진입? 버튼? 값 변경?).
로딩·실패·빈 값일 때 각각 무엇을 반환/표시하나?
같은 데이터를 다시 요청하나, 캐시를 쓰나?
```

- **볼 자리**: 서버 상태 라이브러리의 조회 훅(예: `useQuery`), `fetch` / 요청 함수, `queryKey`, 구독(subscribe).
- **핵심**: 성공 경로 1개가 아니라 **로딩·실패·빈 값** 세 상태를 각각 확인한다.

### 2) 보냄 (쓰기)

```
언제 보내나(어떤 동작이 트리거인가).
보낸 뒤 무엇을 갱신하나(어떤 읽기 데이터를 다시 불러오나)?
실패하면 무엇이 일어나나(되돌리나, 에러 표시만 하나)?
같은 요청을 두 번 못 보내게 막나?
```

- **볼 자리**: 변경 훅(예: `useMutation`), `POST`/`PUT`/`DELETE` 요청, 전송 후 캐시 무효화(invalidate), 낙관적 갱신(optimistic update).
- **핵심**: **성공 후 갱신**과 **실패 후 되돌림**을 반드시 함께 묻는다.

### 3) 담아둠 (보관)

```
이 데이터의 원본(진짜 출처)이 여기냐, 서버냐, 로컬이냐?
언제 값이 바뀌나. 누가 읽나?
앱을 껐다 켜도 남나(영구 저장), 아니면 메모리에만 있나?
```

- **볼 자리**: 전역 상태 저장소(예: Zustand/Redux), 컨텍스트 Provider의 value, 캐시, 로컬 저장소 훅.
- **핵심**: **원본이 어디냐(source of truth)**를 하나로 정한다. 서버 복사본인지, 여기가 원본인지 구분.

### 4) 바꿈 (변형)

```
입력 → 출력 한 줄.
원본 객체/배열을 건드리나, 새로 만들어 반환하나(불변성)?
없는 값·빈 배열이 들어오면 무엇을 반환하나?
```

- **볼 자리**: `select` / 정규화 / `map`·`reduce` / 파생값 계산 함수.
- **핵심**: 화면 이야기 하지 말 것. 데이터 in → 데이터 out만.

## 3. 함수를 붙여 물을 때 (두 번째부터)

파일의 **모든** 함수에 경로를 요청하지 말 것. 필요한 함수만 좁혀서 묻는다.

| 상황                           | 질문                                                                       |
| ------------------------------ | -------------------------------------------------------------------------- |
| 데이터를 가져오는 함수         | `{출처} --데이터--> {도착}`, 그리고 로딩·실패·빈 값 각각                   |
| 데이터를 보내는 함수           | 언제 나가나 + 성공/실패 후 무엇이 갱신/되돌려지나                          |
| 변형만 하는 함수               | 입력 → 출력 한 줄. 원본 건드리나?                                          |
| 한 데이터가 여러 곳에서 갱신됨 | 이 데이터를 바꾸는 지점 **전부**. `{A}--f-->{저장소}`, `{B}--g-->{저장소}` |
| 두 함수가 헷갈림               | `A` vs `B` 무엇이 다른가. 경로 두 줄                                       |

> 다섯 번째 행이 §0 "이유 3"에 대응한다. 한 데이터를 여러 함수가 갱신하면, 어디가 원본인지 흐려진다. **갱신 지점 전부**를 경로로 받아 원본을 하나로 좁힌다.

---

## 4. 하지 말 것

- 성공 경로만 묻고 **실패·빈 값·로딩·미완료**를 빼먹기 (데이터 축에서 가장 흔한 실수)
- 데이터 축과 화면 축을 **한 질문에 섞기** (축은 하나씩)
- 변형 함수에 「언제 요청이 나가나」 같은 읽기 질문 하기
- 전체 스키마·모든 필드를 한 번에 나열 요청하기 (1종류만)
- 모든 함수의 `setState`를 표로 나열 요청하기

「데이터 흐름 그려 줘」라는 요청은 **데이터 파일에는 거의 충분**하다. 다만 `{출처} --데이터--> {도착}` 형식과 "실패·빈 값·로딩도"를 함께 적어 주면 빠짐이 줄어든다.

---

## 5. 경로 감 (힌트, 단정 아님)

| 흔한 이름                                                   | 보통    |
| ----------------------------------------------------------- | ------- |
| `use*Query` `use*Data` `*fetch*` `*load*`                   | 1. 읽기 |
| `use*Mutation` `*save*` `*submit*` `*create/update/delete*` | 2. 쓰기 |
| `*store*` `*context*` `*cache*` `*Provider*` `use*Storage`  | 3. 보관 |
| `*select*` `*normalize*` `*transform*` `*mapTo*` `*format*` | 4. 변형 |

이름은 힌트일 뿐 사실이 아니다. 감이 틀려도 §1이 바로잡는다. 파일은 읽고 나서 고른다.

---

## 6. 화면 축과 이어 보기 (선택)

두 축을 각각 그린 뒤 겹치면 한 바퀴가 된다.

```
{서버 API} --목록--> [목록 화면]          (읽기: 데이터가 화면으로)
[목록 화면] --항목 누름--> [상세 화면]      (화면 전환: 자매 문서 축)
[상세 화면] --저장--> {서버 API}           (쓰기: 화면이 데이터로)
{서버 API} --갱신--> {캐시} --목록--> [목록 화면]   (쓰기 후 갱신)
```

`{ }`는 데이터, `[ ]`는 화면. 한 번에 하나씩 그린 두 지도를 나중에 이렇게 포갠다.
