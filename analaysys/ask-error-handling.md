# 에러 처리 파악 — 질문 요령 (범용)

> **역할**: 파일을 열고 AI에게 물을 때, **함수부터 파지 않고** 무엇이 실패하고 어떻게 잡히는지를 빨리 그리는 법. React / React Native / 웹·앱 공통.
> **자매 문서**: [`ask-file-behavior.md`](./ask-file-behavior.md) 화면(#1), [`ask-data-flow.md`](./ask-data-flow.md) 데이터(#2), [`ask-state-management.md`](./ask-state-management.md) 상태(#3).
> **관계**: 이 문서는 파악의 **4번 축(에러 처리)**이다. 다른 축과 별개로, 한 번에 하나씩 본다.
> **표기**: 실패 지점은 `!네트워크 실패!`처럼 **느낌표 `! !`**. 이어지는 화면 `[ ]`, 데이터 `{ }`, 상태 `( )@소유자`는 자매 문서와 동일. 예: `{서버 API} !실패! --잡음--> (에러 상태) --보임--> [에러 표시]`.
> **에이전트 실행 시**: 축을 시작하기 전에 대상 파일 목록을 고정하고, 축마다 그 목록을 전부 훑는다. 열지 못한 파일은 결과 문서에 "안 읽음"으로 남긴다. 여러 축을 한 번의 조사로 합치지 말 것.

코드 동작의 정본(定本)이 아님. **질문 형식**만 다룬다.

---

## 0. 한 줄 + 왜

코드 조각을 붙여 「이 try/catch 하는 일」부터 물으면 느리다.
**무엇이 실패할 수 있고 → 무엇이 잡고 → 사용자는 무엇을 보고 → 회복되나**를 먼저 그리게 하면, 다음 질문이 갈린다.

### 왜 함수부터 물으면 느린가

- **이유 1 — 에러가 어디까지 퍼지는지 안 잡힌다.**
  `try/catch` 하나만 봐선, 상위에서 또 잡는지, 안 잡혀 앱이 멈추는지 모른다. 실패가 **어디서 멈추나**를 봐야 한다.

- **이유 2 — 삼킨 에러가 안 보인다.**
  가장 흔한 실수다. `catch`만 하고 아무것도 안 하면(빈 `catch`, `console.log`만) 실패가 **조용히 사라져** 디버깅이 안 된다. 함수만 보면 이게 정상처럼 읽힌다.

- **이유 3 — 실패 후 상태·데이터가 어중간하게 남는다.**
  실패했는데 로딩이 안 꺼지거나(영원한 로딩), 저장이 절반만 되거나 한다. **성공 경로만** 물으면 이걸 놓친다.

그래서 **실패 경로**(`!실패! --잡음--> 처리 --보임--> 사용자`)를 먼저 그리게 한다.

---

## 데이터 흐름(#2)과 무엇이 다른가

| 축             | 실패를 다루는 방식                                                      |
| -------------- | ----------------------------------------------------------------------- |
| #2 데이터 흐름 | 데이터 여정의 **한 갈래**로 "실패 시 무엇을 반환/표시" 정도를 잠깐 짚음 |
| #4 에러 처리   | **실패 자체가 주제**. 예방 → 포착 → 표시 → 복구 전 과정을 본다          |

---

## 사용법 (순서)

```
파일을 열었다
        │
        ▼
① 이 파일이 실패를 어떻게 다루는지 모름
        │   →  §1 "첫 질문" 복붙   →  AI가 4종류 중 하나로 답
        ▼
② 종류가 정해졌다
        │   →  §2 에서 그 종류의 질문만 골라 씀
        ▼
③ 두 번째부터: 특정 함수 코드를 붙여 묻는다
            →  §3 "함수를 붙여 물을 때"
```

- **실패 1종류만** 따라간다(예: 네트워크 실패 하나). 모든 `try/catch`를 한 번에 묻지 말 것.

## 1. 첫 질문 (실패를 어떻게 다루는지 모를 때) — 복붙

```
이 파일은 실패를 어떻게 다루나? 아래에 가까운가?
1. 막음 (예방: 입력 검증, 조기 차단, 널 처리)
2. 잡음 (포착: try/catch, 에러 경계, .catch, onError)
3. 보임 (표시: 에러 화면·문구, 알림, 대체 표시)
4. 복구 (되돌림: 재시도, 상태 초기화, 저장 되돌림)

고른 뒤:
1이면 무엇을 어떤 조건에서 막나. 막힌 뒤 사용자는 무엇을 보나?
2이면 무슨 실패를 어디서 잡나. 안 잡히면 어디까지 퍼지나(상위? 앱 정지?)?
3이면 사용자가 무엇을 보나. 아무 표시 없이 넘어가는 실패는 없나?
4이면 실패 후 무엇을 되돌리나. 로딩은 꺼지나, 절반 저장은 없나?

실패 1종류만 따라가. 모든 try/catch 나열하지 마.
```

한 번에 「에러 처리 다 설명해」보다 **종류를 먼저** 고르게 한다.

---

## 2. 종류가 정해진 뒤

### 1) 막음 (예방)

```
무엇을, 어떤 조건에서 막나(검증 규칙)?
막혔을 때 사용자는 무엇을 보나(문구? 비활성화?)?
막지 못하고 통과하는 경우는 없나(빈 값, null)?
```

- **볼 자리**: 입력 검증(validation), 타입 가드, 조기 `return`, 널 처리(`?.` / `??`).
- **핵심**: 실패를 애초에 막는 단계. 통과 구멍이 있는지 함께 본다.

### 2) 잡음 (포착)

```
무슨 실패를 어디서 잡나(try/catch? .catch? 에러 경계? onError?)?
안 잡히면 어디까지 퍼지나(상위 컴포넌트? 앱 정지?)?
잡은 뒤 아무 처리 없이 넘어가진 않나(삼킨 에러)?
```

- **볼 자리**: `try/catch`, `.catch()`, Promise 거부, 에러 경계(컴포넌트 트리에서 하위 렌더 오류를 잡는 장치), 서버 상태 라이브러리의 `onError`(예: TanStack Query).
- **핵심**: **삼킨 에러**(빈 `catch`, 로그만)를 경계한다. 잡은 뒤 뭘 하는지 반드시 확인.

### 3) 보임 (표시)

```
실패 시 사용자가 무엇을 보나(에러 문구? 대체 화면? 알림?)?
아무 표시 없이 조용히 실패하는 경로는 없나?
에러 문구가 사용자가 이해할 말인가, 기술 메시지 그대로인가?
```

- **볼 자리**: 에러 UI 분기, 대체(fallback) 컴포넌트, 알림(toast/alert), 에러 경계의 대체 화면.
- **핵심**: **조용한 실패**(잡았는데 표시가 없음)를 찾는다.

### 4) 복구 (되돌림)

```
실패 후 무엇을 되돌리나(재시도? 상태 초기화? 저장 되돌림?)?
로딩 상태는 확실히 꺼지나?
절반만 처리된 채 남는 데이터·상태는 없나?
```

- **볼 자리**: 재시도(retry)·재요청(refetch), 상태 초기화(reset), 낙관적 갱신 되돌림(rollback).
- **핵심**: **영원한 로딩**과 **절반 저장**이 없는지 확인한다.

---

## 3. 함수를 붙여 물을 때 (두 번째부터)

파일의 **모든** `try/catch`에 지도를 요청하지 말 것. 실패 1종류만 좁혀서 묻는다.

| 상황                       | 질문                                                           |
| -------------------------- | -------------------------------------------------------------- |
| 실패를 잡는 함수           | 이 함수가 잡는 실패만 `!실패! --잡음--> 처리 --보임--> [무엇]` |
| 어디까지 퍼지나 모름       | 여기서 안 잡으면 상위 어디가 잡나, 안 잡혀 앱이 멈추나?        |
| 삼킨 에러 의심             | 이 `catch`는 잡은 뒤 무엇을 하나(표시? 로그만? 아무것도?)?     |
| 한 실패를 여러 곳에서 다룸 | 이 실패를 다루는 지점 **전부**(막음/잡음/보임/복구 중 무엇들)  |
| 두 처리가 헷갈림           | `A` vs `B` 무엇이 다른가. 실패 경로 두 줄                      |

> 세 번째 행이 §0 "이유 2"에 대응한다. `catch` 본문이 비었거나 로그만이면 삼킨 에러다.

---

## 4. 하지 말 것

- **빈 `catch` / `console.log`만** 하고 넘어가기 (삼킨 에러 — 실패가 사라짐)
- 성공 경로만 묻고 **실패 경로를 빼기**
- 실패를 잡았는데 **사용자에게 아무 표시 안 하기** (조용한 실패)
- 실패 후 **로딩 상태를 안 끄기** (영원한 로딩)
- 모든 `try/catch`를 표로 나열 요청하기 (한 실패의 경로만)
- 에러 축과 다른 축을 **한 질문에 섞기** (축은 하나씩)

---

## 5. 경로 감 (힌트, 단정 아님)

| 흔한 표시                                                | 보통    |
| -------------------------------------------------------- | ------- |
| `validate*` `check*` `guard*` `is*` `has*` 조기 `return` | 1. 막음 |
| `try/catch` `.catch` `ErrorBoundary` `onError`           | 2. 잡음 |
| `*Error* UI` `Fallback*` `ErrorState` 알림(toast/alert)  | 3. 보임 |
| `retry*` `refetch` `reset*` `rollback*` `undo*`          | 4. 복구 |

이름은 힌트일 뿐 사실이 아니다. 감이 틀려도 §1이 바로잡는다. 파일은 읽고 나서 고른다.

---

## 6. 다른 축과 이어 보기 (선택)

실패는 데이터·상태·화면 위에 얹혀 흐른다.

```
{서버 API} !요청 실패! --잡음(.catch)--> (에러 상태)@화면 --보임--> [에러 표시]   (포착→상태→표시)
!실패! --복구--> (로딩 상태) = 꺼짐, (입력 상태) = 유지                          (복구: 로딩 끄고 입력 보존)
[저장 버튼] --막음(검증 실패)--> [문구 표시] (요청 안 나감)                        (예방: 애초에 차단)
```

`!` 실패, `[ ]` 화면, `{ }` 데이터, `( )@소유자` 상태. 한 번에 하나씩 그린 지도를 나중에 이렇게 포갠다.
