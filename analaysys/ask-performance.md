# 성능 파악 — 질문 요령 (범용)

> **역할**: 파일을 열고 AI에게 물을 때, **컴포넌트 하나씩 뜯지 않고** 무엇이 자주 다시 도는지를 빨리 그리는 법. React / React Native / 웹·앱 공통.
> **자매 문서**: [`ask-file-behavior.md`](./ask-file-behavior.md) 화면(#1), [`ask-data-flow.md`](./ask-data-flow.md) 데이터(#2), [`ask-state-management.md`](./ask-state-management.md) 상태(#3), [`ask-error-handling.md`](./ask-error-handling.md) 에러(#4), [`ask-types-contracts.md`](./ask-types-contracts.md) 타입(#5).
> **관계**: 이 문서는 파악의 **6번 축(성능)**이다. 다른 축과 별개로, 한 번에 하나씩 본다.
> **표기**: 다시 그림/계산은 `(변화) ⟳ [대상]` — 이 변화가 저것을 다시 그리거나 계산함. 화면 `[ ]`, 데이터 `{ }`, 상태 `( )@소유자`, 실패 `! !`는 자매 문서와 동일.
> **에이전트 실행 시**: 축을 시작하기 전에 대상 파일 목록을 고정하고, 축마다 그 목록을 전부 훑는다. 열지 못한 파일은 결과 문서에 "안 읽음"으로 남긴다. 여러 축을 한 번의 조사로 합치지 말 것.
> 코드 동작의 정본(定本)이 아님. **질문 형식**만 다룬다.

## 0. 한 줄 + 왜 (+ 측정 먼저)

「이 컴포넌트 느리냐」부터 물으면 느리다.
**무엇이 언제 다시 그려지고 → 무엇이 다시 계산되고 → 어디가 실제로 무거운가**를 먼저 그리게 하면, 다음 질문이 갈린다.

> **이 축의 대원칙: 추측하지 말고 측정하라.**
> 성능은 눈으로 짐작하면 엉뚱한 데를 고치기 쉽다. 대부분의 리렌더(다시 그림)는 문제가 아니다. **실제 병목을 측정으로 먼저 찾고**, 그다음 고친다.

### 왜 컴포넌트부터 물으면 느린가

- **이유 1 — 무엇이 트리거하는지 안 잡힌다.**
  느린 건 대개 "이 컴포넌트"가 아니라 "이게 **너무 자주 다시 돈다**"이다. 무엇이 다시 그리는지를 봐야 원인이 나온다.

- **이유 2 — 측정 없이 추측하면 엉뚱한 데를 고친다.**
  대부분의 리렌더는 성능 문제가 아니다. 측정 전에 최적화하면(성급한 최적화) 이득 없이 시간만 쓴다.

- **이유 3 — 최적화가 오히려 비용일 수 있다.**
  불필요한 `useMemo`/`useCallback`·`memo`는 이득 없이 복잡도만 늘린다. 최적화도 **근거(측정)**가 있어야 한다.

그래서 **트리거 지도**(`(변화) ⟳ [대상]`)를 먼저 그리고, 그다음 측정한다.

---

## 상태 관리(#3)와 무엇이 다른가

| 축           | 상태 변화의 무엇을 보나                          |
| ------------ | ------------------------------------------------ |
| #3 상태 관리 | 상태를 **누가 소유하고 언제 바꾸나** (소유·범위) |
| #6 성능      | 그 변화가 **무엇을 얼마나 다시 그리나 (비용)**   |

## 사용법 (순서)

```
파일을 열었다
        │
        ▼
① 이 파일에 어떤 성능 관심사가 있는지 모름
        │   →  §1 "첫 질문" 복붙   →  AI가 4종류 중 하나로 답
        ▼
② 종류가 정해졌다
        │   →  §2 에서 그 종류의 질문만 골라 씀
        ▼
③ 두 번째부터: 특정 컴포넌트·계산 코드를 붙여 묻는다
            →  §3 "코드를 붙여 물을 때"
```

- **관심사 1개만** 따라간다(예: 이 목록의 리렌더). 파일 전체를 한 번에 묻지 말 것.
- **어느 경우든 "이게 실제로 느린가?"를 측정으로 확인한 뒤** 고친다.

## 1. 첫 질문 (어떤 성능 관심사인지 모를 때) — 복붙

```
이 파일의 성능 관심사는 아래에 가까운가?
1. 리렌더 (다시 그림: 무엇이 왜 다시 렌더되나)
2. 재계산 (다시 계산: 무거운 계산이 매 렌더마다 도나)
3. 목록·대량 (긴 리스트·큰 데이터를 그리나)
4. 로드·크기 (초기 로딩, 번들 크기, 이미지·자원)

고른 뒤:
1이면 무엇이 이걸 다시 그리나. (변화) ⟳ [대상]. 그게 실제로 문제인가(측정)?
2이면 어떤 계산이 매 렌더마다 도나. 무거운가, 그냥 값싼가?
3이면 몇 개를 그리나. 가상화(보이는 만큼만) 하나, 전부 그리나?
4이면 초기에 무엇을 다 불러오나. 나중에 미뤄도 되는 건 없나?

측정 전엔 "느리다" 단정하지 마. 무엇이 트리거하는지부터.
```

한 번에 「느린 데 찾아」보다 **관심사를 먼저** 고르고 **측정**을 붙인다.

## 2. 종류가 정해진 뒤

### 1) 리렌더 (다시 그림)

```
무엇이 이 컴포넌트를 다시 그리나. (변화) ⟳ [컴포넌트]
부모가 다시 그릴 때 따라 그리나? 매 렌더 새 객체·함수를 props로 받나?
이 리렌더가 실제로 문제인가(측정), 아니면 값싼 렌더인가?
```

- **볼 자리**: 부모 리렌더, props로 내려가는 인라인 객체/배열/함수(매 렌더 새 참조), 컨텍스트 value 변화.
- **핵심**: 리렌더가 있다고 다 문제는 아니다. **값싼 렌더는 놔둔다.** 참조 동일성(매 렌더 새 객체 = 다른 값 취급)이 흔한 원인.

### 2) 재계산 (다시 계산)

```
어떤 계산이 렌더 본문에서 매번 도나(정렬·필터·큰 map)?
그게 무거운가, 값싼가? 입력이 자주 바뀌나?
메모이제이션(계산 결과 저장·재사용)이 필요한 자리인가, 과한가?
```

- **볼 자리**: 렌더 본문의 정렬/필터/변환, `useMemo` 유무.
- **핵심**: **무거우면서 입력이 안정적일 때만** 메모이제이션이 이득. 값싼 계산에 `useMemo`는 과함.

### 3) 목록·대량

```
몇 개를 그리나. 화면에 보이는 만큼만 그리나(가상화), 전부 그리나?
각 항목의 key가 안정적인가(index 아님)?
스크롤할 때 항목마다 새 함수·객체를 만드나?
```

- **볼 자리**: 긴 `.map`, 리스트 가상화(예: FlatList, FlashList) 유무, `key`, 항목 안 인라인 렌더 함수.
- **핵심**: 항목이 많으면 **가상화**가 기본. `ScrollView` + 전체 `map`은 대량에서 위험.

### 4) 로드·크기

```
초기에 무엇을 다 불러오나(import, 이미지, 라이브러리)?
당장 안 쓰는 화면·기능을 나중으로 미룰 수 있나(지연 로딩)?
큰 자원(이미지·번들)이 초기 로딩을 잡나?
```

- **볼 자리**: 상단 `import` 크기, 지연 로딩(lazy/dynamic import), 이미지 크기, 큰 라이브러리.
- **핵심**: 초기에 꼭 필요한 것만 불러오고 나머지는 미룬다(코드 분할).

## 3. 코드를 붙여 물을 때 (두 번째부터)

파일의 **모든** 컴포넌트에 성능 지도를 요청하지 말 것. 관심사 1개만 좁혀서 묻는다.

| 상황                   | 질문                                                            |
| ---------------------- | --------------------------------------------------------------- |
| 자주 그려지는 컴포넌트 | 무엇이 이걸 다시 그리나 `(변화) ⟳ [대상]`. 실제 문제인가(측정)? |
| 무거워 보이는 계산     | 이 계산이 매 렌더 도나? 무거운가? 메모 대상인가, 과한가?        |
| 긴 리스트              | 몇 개 그리나. 가상화 있나? key 안정적인가?                      |
| 최적화가 이미 있음     | 이 `useMemo`/`memo`가 실제로 이득인가, 불필요한가?              |
| 두 방식이 헷갈림       | `A` vs `B` 어느 쪽이 덜 다시 그리나. 근거는?                    |

> 네 번째 행이 §0 "이유 3"에 대응한다. 이미 붙은 최적화가 근거 없이 들어갔는지 되묻는다.

---

## 4. 하지 말 것

- **측정 없이 최적화**하기 (추측 최적화 — 엉뚱한 데를 고침)
- 모든 컴포넌트에 **`memo`/`useCallback`/`useMemo` 바르기** (불필요한 최적화 = 복잡도 비용)
- "느려 보이는 컴포넌트"를 고치기 전에 **무엇이 트리거하는지 안 보기**
- 긴 리스트를 **가상화 없이 전부 렌더**하기
- **모든 리렌더를 문제로 취급**하기 (대부분 정상)
- 성능 축과 다른 축을 **한 질문에 섞기** (축은 하나씩)

---

## 5. 경로 감 (힌트, 단정 아님)

| 흔한 표시                                                | 보통         |
| -------------------------------------------------------- | ------------ |
| 인라인 객체/함수 props, 컨텍스트 value, 자주 바뀌는 부모 | 1. 리렌더    |
| 렌더 본문의 정렬·필터·큰 map, `useMemo` 대상             | 2. 재계산    |
| 긴 `.map`, `FlatList`, 가상화, `key`                     | 3. 목록·대량 |
| `import`, 지연 로딩(lazy/dynamic), 이미지, 번들          | 4. 로드·크기 |

이름은 힌트일 뿐 사실이 아니다. 감이 틀려도 §1이 바로잡는다. 그리고 **무엇이든 측정으로 확인한 뒤** 고친다.

## 6. 다른 축과 이어 보기 (선택)

성능은 상태·데이터 변화 위에 얹힌 **비용**이다.

```
(검색어 상태) ⟳ [목록] — 매 글자마다 전체 목록 재계산. (측정: 실제 느린가?)
(목록 데이터) ⟳ [FlatList] — 항목 1000개. 가상화 없으면 위험.
부모 리렌더 ⟳ [자식] — 인라인 함수 props가 매번 새 참조. (값싸면 놔둠)
```

`⟳` 다시 그림/계산, `[ ]` 화면·컴포넌트, `( )@소유자` 상태, `{ }` 데이터. 한 번에 하나씩 그린 지도를 나중에 이렇게 포갠다. **어느 경우든 측정이 먼저다.**
