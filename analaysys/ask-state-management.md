# 상태 관리 파악 — 질문 요령 (범용)

> **역할**: 파일을 열고 AI에게 물을 때, **함수부터 파지 않고** 상태를 누가 들고 언제 바꾸는지를 빨리 그리는 법. React / React Native / 웹·앱 공통.
> **자매 문서**: [`ask-file-behavior.md`](./ask-file-behavior.md) 화면 흐름(#1), [`ask-data-flow.md`](./ask-data-flow.md) 데이터 흐름(#2).
> **관계**: 이 문서는 파악의 **3번 축(상태 관리)**이다. 다른 축과 별개로, 한 번에 하나씩 본다.
> **표기**: 상태는 `(선택된 항목)@목록화면`처럼 **소괄호 `( )`** 에 상태 이름, `@` 뒤에 소유자. 화면은 `[ ]`, 데이터 지점은 `{ }`(자매 문서와 동일).
> **에이전트 실행 시**: 축을 시작하기 전에 대상 파일 목록을 고정하고, 축마다 그 목록을 전부 훑는다. 열지 못한 파일은 결과 문서에 "안 읽음"으로 남긴다. 여러 축을 한 번의 조사로 합치지 말 것.
> 코드 동작의 정본(定本)이 아님. **질문 형식**만 다룬다.

---

## 0. 한 줄 + 왜

코드 조각을 붙여 「이 함수 하는 일」부터 물으면 느리다.
**이 상태를 누가 소유하고 → 언제 바뀌고 → 어디까지 퍼지나**를 먼저 그리게 하면, 다음 질문이 갈린다.

### 왜 함수부터 물으면 느린가

- **이유 1 — 소유자가 안 잡힌다.**
  함수만 물으면 "이 함수는 값을 바꾼다"는 답은 받는다. 그런데 그 상태를 **누가 들고 있는지**(지역인지 전역인지)가 안 보인다.

- **이유 2 — 같은 상태를 여러 곳에서 바꾸면 어긋난다.**
  하나의 상태를 여러 함수가 갱신하면, 순서·타이밍이 꼬여 값이 어긋난다(동기화 문제). 갱신 지점을 한 번에 봐야 드러난다.

- **이유 3 — 파생값을 따로 저장하면 낡은 값이 된다.**
  다른 상태에서 계산되는 값(파생 상태, derived state)을 별도 상태로 저장하면, 원본이 바뀌어도 안 따라와 **낡은 값(stale)**이 된다. **원본은 하나로 정하고, 나머지는 계산**으로 얻는다.

그래서 **상태 지도**(`(상태)@소유자`, `트리거 --설정--> (상태)`)를 먼저 그리게 한다.

## 데이터 흐름(#2)과 무엇이 다른가

| 축             | 묻는 것                                                                                              |
| -------------- | ---------------------------------------------------------------------------------------------------- |
| #2 데이터 흐름 | 데이터 1건이 **출처 → 도착 어디로 흐르나** (여정)                                                    |
| #3 상태 관리   | 그 상태를 **누가 소유하고, 어디까지 퍼지고, 언제 바뀌고, 어긋나지 않게 유지되나** (소유·범위·동기화) |

겹치는 부분(#2의 "담아둠")이 있지만 초점이 다르다. #2는 흐름, #3은 소유와 범위다.

## 사용법 (순서)

```
파일을 열었다
        │
        ▼
① 이 파일이 상태를 어떻게 두는지 모름
        │   →  §1 "첫 질문" 복붙   →  AI가 4종류 중 하나로 답
        ▼
② 종류가 정해졌다
        │   →  §2 에서 그 종류의 질문만 골라 씀
        ▼
③ 두 번째부터: 특정 함수 코드를 붙여 묻는다
            →  §3 "함수를 붙여 물을 때"
```

- **상태 1개만** 따라간다. 모든 `useState`를 한 번에 묻지 말 것.

## 1. 첫 질문 (상태를 어떻게 두는지 모를 때) — 복붙

```
이 파일은 상태를 어떻게 두나? 아래에 가까운가?
1. 지역 상태 (이 컴포넌트 안에서만 씀)
2. 공유 상태 (부모가 들고 자식에 내려줌 / 끌어올린 상태)
3. 전역 상태 (앱 전체 저장소·컨텍스트)
4. 파생 상태 (다른 상태에서 계산되는 값)

고른 뒤:
1이면 어떤 값이 지역 상태냐. 이 컴포넌트 밖에서 필요해지진 않나?
2이면 누가 원본을 들고(어느 부모), 누가 읽고, 누가 바꾸나? 몇 단계 내려가나?
3이면 진짜 전역이어야 하나? 누가 바꾸고 누가 구독하나? 서버 데이터와 섞였나?
4이면 원본이 무엇이냐. 원본이 바뀌면 자동으로 따라오나, 수동이라 어긋날 수 있나?

상태 1개만 따라가. 모든 useState 나열하지 마.
```

한 번에 「상태 다 설명해」보다 **종류를 먼저** 고르게 한다.

---

## 2. 종류가 정해진 뒤

### 1) 지역 상태 (local)

```
어떤 값이 이 컴포넌트만의 상태인가.
언제 바뀌나(어떤 동작이 트리거인가)?
이 값이 다른 화면·컴포넌트에서도 필요해질 여지가 있나?
```

- **볼 자리**: `useState` / `useReducer` 선언. setter를 밖으로 안 넘기면 지역 상태다.
- **핵심**: 지금 지역으로 충분한지, 나중에 공유가 필요해질지 구분한다.

### 2) 공유 상태 (끌어올린 상태, lifted)

```
누가 원본을 들고(어느 부모 컴포넌트), 누가 읽나, 누가 바꾸나(콜백)?
props가 몇 단계 내려가나(prop drilling)?
(선택) 콜백으로 바꾸나, 바로 setter를 내려주나?
```

- **볼 자리**: 부모의 `useState` + 자식에 내려주는 `value`/`on*`/`set*` props.
- **핵심**: **원본은 부모 하나**. 자식은 읽고, 바꿀 땐 콜백을 부른다. 너무 깊이 내려가면(prop drilling) 전역 후보.

### 3) 전역 상태 (global)

```
이게 진짜 전역이어야 하나(정말 여러 화면이 쓰나)?
누가 바꾸고(액션·setter), 누가 구독하나?
서버에서 온 데이터를 여기에 통째로 복사해 두진 않았나?
```

- **볼 자리**: 전역 상태 라이브러리(예: Zustand, Redux)의 훅, 컨텍스트 Provider의 `value`.
- **핵심**: **불필요한 전역**을 경계한다. 서버 데이터는 전역 상태가 아니라 서버 상태 라이브러리(예: TanStack Query) 영역인 경우가 많다.

### 4) 파생 상태 (derived)

```
이 값의 원본이 무엇이냐. 원본 → 이 값, 계산 한 줄.
이걸 별도 상태로 저장했나, 그때그때 계산하나?
저장했다면 원본이 바뀔 때 어떻게 맞추나(수동 동기화면 어긋날 위험)?
```

- **볼 자리**: `useMemo`로 계산한 값(좋음) vs `useState`에 저장하고 `useEffect`로 맞추는 값(어긋남 위험 신호).
- **핵심**: **원본 하나 + 계산**이 기본. 파생값을 상태로 저장하는 것은 낡은 값의 흔한 원인.

---

## 3. 함수를 붙여 물을 때 (두 번째부터)

파일의 **모든** 함수·상태에 지도를 요청하지 말 것. 필요한 상태 1개만 좁혀서 묻는다.

| 상황                       | 질문                                                                 |
| -------------------------- | -------------------------------------------------------------------- |
| 상태를 바꾸는 함수         | 이 함수가 바꾸는 상태만 `트리거 --설정--> (상태)@소유자`             |
| 소유자가 헷갈림            | 이 상태의 원본이 어디냐(지역/부모/전역)? `(상태)@소유자` 한 줄       |
| 한 상태를 여러 곳에서 바꿈 | 이 상태를 바꾸는 지점 **전부**. `[A]--f-->(상태)`, `[B]--g-->(상태)` |
| 파생값이 의심됨            | 이건 원본이냐 계산값이냐? 계산값이면 원본은 무엇                     |
| 두 상태가 헷갈림           | `A` vs `B` 무엇이 다른가. 소유·갱신 두 줄                            |

> 세 번째 행이 §0 "이유 2"에 대응한다. 한 상태를 여러 함수가 바꾸면, **갱신 지점 전부**를 받아 어긋남 위험을 드러낸다.

---

## 4. 하지 말 것

- **파생값을 `useState`로 저장하고 `useEffect`로 동기화**하기 (원본 하나 + 계산으로 대체)
- 지역 상태로 충분한데 **전역에 올리기** (불필요한 전역)
- **서버 데이터를 전역 상태에 통째로 복사**해 수동 관리하기 (서버 상태 라이브러리 영역)
- **같은 상태를 두 곳에 각각 저장**하기 (원본이 둘 → 어긋남)
- 모든 `useState`를 표로 나열 요청하기 (상태 1개의 소유·갱신 경로만)
- 상태 축과 화면·데이터 축을 **한 질문에 섞기** (축은 하나씩)

---

## 5. 경로 감 (힌트, 단정 아님)

| 흔한 표시                                        | 보통              |
| ------------------------------------------------ | ----------------- |
| `useState` `useReducer` (setter를 밖에 안 넘김)  | 1. 지역           |
| props로 내려가는 `on*` `set*` 콜백               | 2. 공유(끌어올린) |
| `*Context*` `*Provider*` `use*Store` `*store*`   | 3. 전역           |
| `useMemo` `derived*` `computed*` selector `get*` | 4. 파생           |

이름은 힌트일 뿐 사실이 아니다. 감이 틀려도 §1이 바로잡는다. 파일은 읽고 나서 고른다.

## 6. 다른 축과 이어 보기 (선택)

상태는 화면(#1)과 데이터(#2)를 잇는 자리에 있다.

```
{서버 API} --목록--> (목록 상태)@목록화면 --그림--> [목록 화면]   (데이터→상태→화면)
[버튼] --선택--> (선택된 항목)@목록화면                        (화면 동작→상태)
(선택된 항목) --파생--> (버튼 활성 여부)                        (파생: 저장 말고 계산)
```

`[ ]` 화면, `{ }` 데이터, `( )@소유자` 상태. 한 번에 하나씩 그린 지도를 나중에 이렇게 포갠다.
