# 테스트 파악 — 질문 요령 (범용)

> **역할**: 테스트 파일을 열고 AI에게 물을 때, **테스트 코드를 줄줄 읽지 않고** 무슨 동작을 지키는지를 빨리 그리는 법. React / React Native / 웹·앱 공통.
> **자매 문서**: [`ask-file-behavior.md`](./ask-file-behavior.md) 화면(#1), [`ask-data-flow.md`](./ask-data-flow.md) 데이터(#2), [`ask-state-management.md`](./ask-state-management.md) 상태(#3), [`ask-error-handling.md`](./ask-error-handling.md) 에러(#4), [`ask-types-contracts.md`](./ask-types-contracts.md) 타입(#5), [`ask-performance.md`](./ask-performance.md) 성능(#6).
> **관계**: 이 문서는 파악의 **7번 축(테스트)**이다. 다른 축과 성격이 다르다 — 테스트는 **다른 여섯 축의 동작이 안 깨지게 고정**하는 축이다.
> **표기**: 테스트는 `상황 → 동작 → ✓기대`(상황-동작-기대). 화면 `[ ]`, 데이터 `{ }`, 상태 `( )@소유자`, 실패 `! !`, 다시 그림 `⟳`는 자매 문서와 동일.
> **에이전트 실행 시**: 축을 시작하기 전에 대상 파일 목록을 고정하고, 축마다 그 목록을 전부 훑는다. 열지 못한 파일은 결과 문서에 "안 읽음"으로 남긴다. 여러 축을 한 번의 조사로 합치지 말 것.
> 코드 동작의 정본(定本)이 아님. **질문 형식**만 다룬다.

---

## 0. 한 줄 + 왜

테스트 코드를 붙여 「이 테스트 뭐 하냐」부터 줄줄 물으면 느리다.
**무엇을(대상) → 어느 수준에서 → 무엇을 확인하고(기대) → 무엇을 가짜로 두나**를 먼저 그리게 하면, 다음 질문이 갈린다.

### 왜 테스트 코드부터 읽으면 느린가

- **이유 1 — 무슨 동작을 지키는지 안 잡힌다.**
  테스트는 "이 동작이 안 깨지게 지킨다"는 약속(회귀 방지 — 고쳤던 게 다시 깨지지 않게)이다. 코드 줄이 아니라 **무슨 동작을 고정하는지**부터 봐야 한다.

- **이유 2 — 구현을 테스트하면 리팩터에 깨진다.**
  내부 함수 이름·상태를 검사하면, **동작은 그대로인데 리팩터만 해도** 테스트가 깨진다. 사용자가 보는 **동작**을 검사해야 한다(동작 > 구현).

- **이유 3 — 과한 가짜(mock)는 테스트를 무의미하게 만든다.**
  다 가짜로 바꾸면 "가짜끼리 잘 논다"만 확인한다. **무엇을 진짜로 두고 무엇을 가짜로 둘지**가 테스트 가치를 정한다.

그래서 **동작 지도**(`상황 → 동작 → ✓기대`)를 먼저 그리게 한다.

---

## 다른 축과의 관계

테스트는 "vs 어느 축"이 아니라, **다른 여섯 축의 동작을 검증**한다.

```
{서버 실패} → 앱이 잡음 → ✓[에러 표시] 보임        (에러 축 #4 동작을 고정)
(빈 목록 상태) → 렌더 → ✓"항목 없음" 표시           (상태·화면 동작을 고정)
[항목 클릭] → ✓[상세 화면]으로 이동                  (화면 흐름 #1 동작을 고정)
```

즉 앞 축들에서 그린 지도가 **실제로 그렇게 동작하는지**를 테스트가 지킨다.

## 사용법 (순서)

```
테스트 파일을 열었다
        │
        ▼
① 이 테스트가 어느 수준인지 모름
        │   →  §1 "첫 질문" 복붙   →  AI가 4종류 중 하나로 답
        ▼
② 수준이 정해졌다
        │   →  §2 에서 그 수준의 질문만 골라 씀
        ▼
③ 두 번째부터: 특정 테스트 코드를 붙여 묻는다
            →  §3 "테스트를 붙여 물을 때"
```

- **동작 1개만** 따라간다(예: "빈 목록일 때"). 파일의 모든 `it`을 한 번에 묻지 말 것.

---

## 1. 첫 질문 (어느 수준인지 모를 때) — 복붙

```
이 테스트는 어느 수준인가? 아래에 가까운가?
1. 단위 (함수·순수 로직 하나: 입력 → 출력)
2. 컴포넌트 (렌더·상호작용: 누르면 무엇이 보이나)
3. 통합 (여러 조각 함께: 데이터+상태+화면 흐름)
4. E2E (끝에서 끝: 실제 앱처럼 시나리오 전체)

고른 뒤:
1이면 입력 → 기대 출력. 경계값·빈 값도 확인하나?
2이면 상황 → 동작 → ✓기대. 사용자가 보는 것을 검사하나, 내부 상태를 검사하나?
3이면 무엇을 진짜로 두고 무엇을 가짜(mock)로 두나?
4이면 어떤 시나리오 전체를 밟나. 불안정(됐다 안 됐다)하진 않나?

무슨 동작을 지키는지부터. 코드 줄 나열하지 마.
```

한 번에 「이 테스트 파일 설명해」보다 **수준을 먼저** 고르게 한다.

---

## 2. 종류가 정해진 뒤

### 1) 단위 (unit)

```
입력 → 기대 출력 한 줄.
경계값·빈 값·잘못된 입력도 확인하나?
순수 함수인가(같은 입력 → 같은 출력), 바깥 의존이 있나?
```

- **볼 자리**: 순수 함수 테스트, 입력·기대 출력 쌍, `describe`/`it`/`expect`.
- **핵심**: 성공 케이스만 있나, 경계·실패도 있나 확인.

### 2) 컴포넌트 (component)

```
상황 → 동작 → ✓기대. (렌더 → 누름 → 무엇이 보이나)
사용자가 보는 것을 검사하나(문구·역할), 내부 상태·함수명을 검사하나?
```

- **볼 자리**: 렌더 + 사용자 상호작용(클릭/입력) + 화면 조회(예: Testing Library의 `getByText`/`getByRole`).
- **핵심**: **동작을 검사**한다. 내부 구현 검사(§0 이유 2)면 리팩터에 약하다.

### 3) 통합 (integration)

```
어떤 조각들이 함께 도나(컴포넌트+훅+데이터)?
무엇을 진짜로 두고 무엇을 가짜(mock)로 두나?
가짜가 너무 많아 "가짜끼리 잘 논다"만 확인하진 않나?
```

- **볼 자리**: 여러 컴포넌트/훅 함께, 가짜로 끼운 API + 실제 상태 흐름.
- **핵심**: **진짜/가짜 경계**가 테스트 가치를 정한다(§0 이유 3).

### 4) E2E (끝에서 끝)

```
어떤 시나리오 전체를 밟나(로그인 → 목록 → 저장 등)?
실제 앱을 구동하나? 불안정(같은 코드인데 됐다 안 됐다)하진 않나?
```

- **볼 자리**: 시나리오 스텝, 실제 구동, E2E 도구(예: Detox, Playwright, Cypress)의 셀렉터.
- **핵심**: 느리고 깨지기 쉬우므로 **핵심 시나리오만** 얇게. 불안정 테스트를 경계.

---

## 3. 테스트를 붙여 물을 때 (두 번째부터)

파일의 **모든** `it`에 설명을 요청하지 말 것. 동작 1개만 좁혀서 묻는다.

| 상황                    | 질문                                                                     |
| ----------------------- | ------------------------------------------------------------------------ |
| 이 테스트가 지키는 동작 | `상황 → 동작 → ✓기대` 한 줄로만                                          |
| 구현 테스트 의심        | 이건 동작을 검사하나, 내부 상태·함수명을 검사하나?                       |
| 가짜가 많음             | 무엇이 진짜고 무엇이 가짜(mock)인가? 이 테스트가 실제로 무엇을 보장하나? |
| 커버리지 이야기         | 이 줄들이 테스트에 닿긴 하나, 동작을 **확인**은 하나?                    |
| 두 테스트가 헷갈림      | `A` vs `B` 무슨 동작 차이를 지키나. 두 줄                                |

> 네 번째 행: 커버리지(코드가 테스트에 닿은 비율)가 높아도 **확인(assert)이 없으면** 지키는 게 없다. 숫자만 쫓지 않는다.

---

## 4. 하지 말 것

- **구현 세부를 테스트**하기 (내부 상태·함수명 검사 → 리팩터에 깨짐)
- **다 가짜(mock)로 바꿔** 무의미하게 만들기 ("가짜끼리 잘 논다"만 확인)
- **커버리지 숫자만 쫓기** (닿는 것 ≠ 확인하는 것; 100%가 좋은 테스트는 아님)
- 스냅샷 테스트에만 의존하기 (흔하지만, 무엇이 왜 깨졌는지 안 알려줘 신호가 약함)
- 테스트 코드를 **줄줄 읽기 전에** 무슨 동작 지키는지 안 묻기
- 테스트 축과 다른 축을 **한 질문에 섞기** (축은 하나씩)

---

## 5. 경로 감 (힌트, 단정 아님)

| 흔한 표시                                       | 보통        |
| ----------------------------------------------- | ----------- |
| `*.test.ts` `*.spec.ts` 순수 함수 + `expect`    | 1. 단위     |
| `render()` + `fireEvent`/`userEvent` + `getBy*` | 2. 컴포넌트 |
| 여러 컴포넌트/훅 + 가짜 API(`mock`)             | 3. 통합     |
| `*.e2e.*` 시나리오 스텝, E2E 도구(예: Detox)    | 4. E2E      |

이름은 힌트일 뿐 사실이 아니다. 감이 틀려도 §1이 바로잡는다. 파일은 읽고 나서 고른다.

---

## 6. 7축 마무리

테스트(#7)는 앞 여섯 축을 검증하는 자리다. 한 기능을 볼 때, 축을 하나씩 그린 뒤 마지막에 "이 동작들이 테스트로 지켜지나"를 얹으면 한 바퀴가 닫힌다.

```
[화면 #1] · {데이터 #2} · (상태 #3) · !에러 #4! · 계약 #5 · 성능 #6
        └───────────────  ✓ 테스트 #7 이 전부를 고정  ───────────────┘
```

각 축은 **한 번에 하나씩**. 동시에 다 보면 복잡해 이해가 흐려진다. 하나씩 그린 지도를 나중에 포갠다.
